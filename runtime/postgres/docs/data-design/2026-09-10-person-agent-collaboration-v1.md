## 1. 框架与 MVP

全社区使用同款框架：人担任岗位，在工作范围内与智能体合作，按明确动作授权做事。组织图是这些关系的视图，不是授权来源。一栋与二花只是实例；换人、代理、增加智能体、调整群聊均不另建体系。

职责采用“少量动作类别 + 业务领域 + 明确范围”，自然语言描述工作目标、具体主题和习惯。厨房、值日、设施等无需穷举为权限；自然语言也不能自行增加权限类别、楼栋或数据可见性。岗位模板可以预填，必须由有相应管理权的人保存才生效。

MVP 包含关系配置、当前授权判断、合作启动、信息待确认闭环和旧入口接入。欢迎消费这套服务。基金、值日等完整业务应用按需另接，既不全部塞进本轮，也不成为欢迎的前置条件。

## 3. 最小关系模型

下列新表拟放在
`qintopia_agent_os`。主键为 UUID；外键默认禁止删除仍被引用的历史对象。控制记录共用
`tenant_key`、`version`、创建/更新时刻、创建操作者引用；有效关系另有
`status`、`valid_from`、`valid_until`、撤销时间及原因。有效时间为左闭右开区间，均使用 UTC。

### 3.1 范围、任职和合作

| 拟定表                         | 关键字段、外键与约束                                                                                                      | 用途                                                                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `collaboration_scopes`         | `id, tenant_key, scope_key, kind, label, parent_scope_id`；租户内 scope_key 唯一；父范围同租户且不能成环                  | 公司、社区、楼栋、业务范围；层级用于表达归属，不自动继承权限                                        |
| `collaboration_scope_bindings` | `scope_id, binding_kind, conversation_id?, source_instance?, property_ref?`；按 kind 校验字段；会话引用现有 conversations | 将范围关联群或 PMS 物业；活动绑定不得重复，变更保留旧版本                                           |
| `collaboration_roles`          | `id, role_key, label, responsibility_text`；租户内 role_key 唯一                                                          | 可调整的岗位定义；岗位名称和描述本身不赋权                                                          |
| `collaboration_appointments`   | `person_id, role_id, scope_id, replaces_id?, proxy_for_id?`；均有外键                                                     | 任职、复任、代理是不同记录；同人同岗同范围不得有重叠有效任期                                        |
| `agent_collaborations`         | `appointment_id, agent_key, scope_id, domain_key, responsibility_text`                                                    | 每条关系对应一项任职、一个 Agent、一个范围和领域；多对多用多条关系表达                              |
| `collaboration_grants`         | `collaboration_id, action_key, scope_id, domain_key, parent_grant_id?, delegation_depth`                                  | 按动作单独授权；同关系/动作/范围/领域的有效授权不能重叠                                             |
| `collaboration_agreements`     | `collaboration_id, revision, confirmed_by, confirmed_at, agreement_artifact_id, settings`                                 | 保存重点、工作节点、汇报/提醒习惯、升级方式和业务确认人引用；同关系 revision 唯一，仅一个当前确认版 |

关系范围和授权范围必须落在任职与授予者可管理范围的交集内。跨多个群以明确绑定表达；一个群可承载多个业务范围，但请求必须确定本次范围，歧义时不把各范围权限合并。私聊接待不要求预先给每位联系人建立合作关系。

范围绑定变更也是授权管理动作，须检查新增对象是否在操作者可管理集合内，递增范围版本并使待执行旧许可失效；不能通过“编辑群标签”绕过扩大范围的检查。关系和授权使用 draft/active/ended/revoked 状态，active 仍需检查当前任期；任职结束不删除历史。

`agent_key`
不能对 YAML 建数据库外键：写入服务核对 registry 版本，执行时再核对 Agent 是否可用。未注册的客房智能体可显示为规划占位，不能保存成有效可执行授权；Agent 下线后保留历史关系，停止新执行。

动作类别至少区分信息提交、知识确认、范围内训练、规则调整、内容审核、发布、业务确认人指定、身份关联管理和组织授权管理。它们不是每个生活事项的清单。技术支持使用同款关系，具体技术动作由 capability 注册表表达；技术岗位不自动获得业务裁定、秘密读取或部署权。

执行权和管理权分开：`parent_grant_id`
追溯管理授权来源，管理授权明确可授出的动作、Agent、领域和范围。授予者不必亲自执行每项业务，但不能超出自己的可授予集合；默认不可再转授，明确配置后才允许有限转授。撤销上级管理授权使依赖它的下级授权失效，不能靠重新保存关系恢复。

知识版本状态为 pending/confirmed/rejected/superseded/revoked；过期由有效时间判断。

生效时间依据：
[2026-09-22 规则生效时间决定](../../../../docs/plans/active/unified-person-welcome-v1-contract.md#本栋规则的生效时间负责人确认2026-09-22)。

确认状态与当前适用版本分别判断：同一作用范围内的 item_key 在任一时刻最多一个当前生效版本，允许保存已经确认但尚未到生效时间的后继版本。

规则未指定生效时间时，成功持久保存后立即生效；指定未来时间时，记录独立的保存时间和业务生效时间。未来版本保存时不能把当前有效版本提前标为 superseded，也不能让其确认状态绕过 valid_from。版本登记、前后版本的生效区间及替换关系须在同一事务内保持一致；检索按当前时刻选取有效版本，保存前仍核对当前权限和版本。这里更新的是设计契约，知识版本存储和消费者尚待实现。

agent_key 为空仅表示该知识可供范围内获授权的多个 Agent 使用，不表示全局可见。

普通反馈只保存必要信息及来源引用。私聊个人烦恼、服务偏好、公共生活线索分别处理；不自动保存整段聊天或转成共享知识。原始秘密不进审计摘要。`expires_at`
控制业务有效期，实际删除保留期沿用对应内容域已有政策。社区成员及获准个人记忆按[长期社区记忆决定](../../../../docs/plans/active/unified-person-welcome-v1-contract.md#长期社区成员来访历史与当前状态负责人确认2026-09-22)保留，不以离店或闲置期限清除；该原则不扩大到全部原始聊天、秘密或任意业务资料。没有适用政策的其他内容不启用批量导入或无限期保存，启用前补具体保留策略。

暂不增加通用受众表：本次对象选择作为 WorkItem 的版本化输入，解析结果作为受限 Artifact，逐目标结果复用现有执行模型。暂不新增聊天历史库或重建知识正文库。

### 3.3 一致性和生命周期

- 同租户关系使用组合外键或事务校验，禁止跨租户关联。复用无 tenant 字段的 Person 时，由已核验的租户渠道绑定检查访问权，不能仅凭 person_id 读取资料。
- 有效任期重叠使用数据库排他约束或带锁的等价约束；当前版唯一约束不依赖易变的 `now()`
  索引条件。所有写入带 expected_version，冲突返回当前版本供重读。
- 命令去重、对象变更和审计在同一数据库事务提交；异步执行持久创建 WorkItem 后返回任务引用。进程退出不能留下“已确认但无任务”的半状态。
- 授权变更与执行许可获取锁定同一授权版本，形成可判定的先后次序。准备阶段的批准不是长期执行票据；实际出站前复核当前身份、任职、授权、对象、内容版本、联系偏好和执行模式。
- 已交给外部渠道的请求不能追溯撤回。撤权阻止尚未取得最终执行许可的动作；已许可并在途的动作留审计并核对回执，不声称可取消，也不在 unknown 状态重发。
- 撤权/代理到期同时使缓存和未执行旧许可失效。授权服务不可用时受控写入、受限读取和主动发送失败关闭；普通公开咨询按已部署接待能力处理，不借故读取旧缓存中的私密资料。

## 4. UI 设置如何真正生效

```text
UI 选择人员、智能体、范围和职责 / 对话提出修改
  → 服务端从可信会话解析操作者（不相信模型自报身份）
  → 验证当前管理权，生成具体变更预览
  → 用户明确保存 / 对话明确确认具体变更
  → 同一受控命令服务持久化、版本检查、审计
  → 训练、知识检索、审核、找人、发送入口读取当前授权
  → 执行层复核并记录结果
```

普通信息提交不要求训练权限；其结果保持待确认。自然语言可以整理配置草稿，不能直接写库或把聊天中的角色声明当任命。可信渠道映射冲突、共享账号无法识别真人时，权限操作进入身份核验出口。

本栋规则变更按以下已确认条款识别指令：
[2026-09-22 修改指令决定](../../../../docs/plans/active/unified-person-welcome-v1-contract.md#本栋规则的修改指令负责人确认2026-09-22)。

内容和范围清楚的修改指令本身构成请求人的确认；具有相应自主权限时，无需额外确认轮次，由同一受控服务核验并保存，成功后告知结果。建议性表达保持待确认提议，实质歧义才澄清。请求人的确认不代替权限模式要求的指定他人确认；模型也不能绕过服务直接写库。本条不把本栋规则的确认方式扩展为组织配置或任命的默认行为。

新有效合作关系创建可恢复的启动 WorkItem。智能体介绍现有职责、知识、待办和能力限制，提出少量具体建议，引导责任人确定工作重点、汇报节点、提醒习惯和升级方式；整理复述，经本人确认后生成合作约定当前版。频率不在代码中替舍长决定。

## 10. F1 职责连接与权限补充实现（2026-09-10.003）

用户恢复开发后，按[本轮实现约定](../../../../docs/plans/active/collaboration-duties-permissions-implementation.md)
追加迁移 `.003`；前面的设计讨论记录保留其当时状态。

| 数据对象                                            | 新增内容                               | 业务含义                                                         |
| --------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| `collaboration_duties`                              | 名称、说明、领域、适用权限、状态、版本 | 独立维护“居民服务”等职责，不把权限名称当职责                     |
| `collaboration_roles` / `collaboration_role_duties` | 岗位说明、状态、版本与职责关联         | 预置岗位和新增岗位采用相同维护入口                               |
| `agent_collaborations`                              | `duty_id`、`replaces_id`               | 一条连接绑定完整的人、岗、责、智能体、范围；换人或范围保留原连接 |
| `collaboration_grants`                              | `decision_mode`、`reviewer_person_id`  | 同一权限明确自主、需确认或未授予，不以自然语言描述自动赋权       |

权限是少量能力类别的明确授权；具体厨房、钥匙、公共空间等事项在职责范围内处理，不逐项建生活事项白名单。普通提供信息不需要岗位权限。自然语言解释边界，但不直接转成执行许可。

确认人必须为其他已核验自然人，且在相同职责、智能体、领域和范围内拥有该项自主权限；每次判断重查身份、任职、有效期及授权来源。确认人失效时拒绝，不能改为自主或另找任意人。管理授权本身为需确认时，不可授予其他权限、创建岗位或读取管理工作台。
`/api/decision`
只解释当前配置，不是业务批准、执行票据，也不代替具体流程对内容、目标、版本的确认。

修改岗位或职责可选方案不产生新授权。移除正在使用的职责／权限类别或停用仍有当前引用的对象会拒绝；先处理明确的相关连接。无历史对象可删除，有历史对象停用并保留记录。连接替换、结束、权限更新仍复用同一事务、版本冲突、幂等命令和审计；失败或预览不留下半次交接。结束最后一条连接时结束空任职，其他任职与连接不受影响。

兼容策略：旧记录的 `duty_id`
不做猜测填充；旧业务授权缺少职责时不能自主放行。仅本地初始化管理链继续受控管理，普通入口禁止撤销或改写该根连接。迁移仅为具名本地测试租户补充职责定义及“秦托邦”名称，不为任何真人或真实系统新增授权。

界面提供总览、人、智能体、岗位、职责、范围六个入口与独立连接编辑。本地可保存配置，但真实登录、runtime、合作启动、知识确认、开放接待、主动私聊及渠道发布仍需后续接入。本轮没有修改 PMS 共同协议、Hermes
profile、生产数据库或外部配置，没有发送消息。专项验收结果记录在本轮交付报告，不能用历史测试结果替代。
