## 1. 目标、责任与依据

岸岸（`anan`）是配合小客服和刘珊操作 Green
PMS 的客房协作智能体。工作人员可以直接通过企业微信交办查询、订房、收款登记及住宿安排，不必先有申请表或收款事件。岸岸主动查询、整理和建议；订房及房态变化优先与小客服确认，小客服无法确认时交刘珊。

正常订单无需逐笔交四老师或主管再审。主管与四老师维护经营规则和经验，岸岸消费有效版本。

```text

                                      ↕
                       Agent OS 身份、授权、事项、确认与回执
```

查询可在鉴权后直接返回；等待确认、业务写入、后台恢复和跨 Agent 协作使用既有持久任务机制。PMS 请求无需统一经过一个新建中转服务。首期不创建独立 MCP
Server、通用能力目录平台或新人员数据库；未来多个调用方确需复用、或进程隔离确有需要时，再评审提取共享客户端/执行组件。

Skill、申请内容、聊天原文和 PMS 文本字段都是业务数据或工作说明，不能替代程序层授权。

## 4. 对话办理业务流程

### 4.1 受理与查询

1. Gateway 提供可信平台、机器人、发送者、会话和消息引用；模型不能自行填“我是小客服”获得权限。
2. 共同身份服务解析人、任职与范围；PMS
   Token 返回的权限只代表岸岸执行主体，不证明发言人有相同权限。
3. 查询订单、人员、住宿历史、可售房源或收款候选；响应裁剪到当次用途及受众，群里不展示完整证件/联系方式。
4. 复用可靠的 Person/PMS 来源关联；同名、昵称或金额仅作候选，歧义只询问当次业务必需信息。
5. 岸岸用业务语言说明可做什么、查到什么、缺什么。简单查询不要求新申请、事先收款或额外审批。

### 4.2 建立预订

1. 收到订房交办后建立/恢复事项，收集最终到离日期、晚数、人数、房床、住客必需信息、价格和渠道。
2. 查询 PMS 当前可售及报价；按有效经营规则提供建议和理由。可调整建议不能冒充硬性规则。
3. 以 PMS
   Quote/Preview 形成可核对方案。解释房间、日期、价格、占用库存等实际影响，不让用户理解 API 名词。
4. 由有权小客服确认本次方案；无法确认时交刘珊。明确指令已覆盖相同方案时可作有效确认，不重复索要同一决定。
5. 工具绑定确认人、可信消息、事项版本、PMS 预览和效果摘要；执行前重新检查权限、有效期和业务依据。
6. 调用 PMS
   Confirm，取得实际结果和回执后回复订单及安排；预览成功、受理成功不能说成“已订好”。

有效人类确认与 PMS 技术 Preview/Confirm 是不同层次，不要求人机械点两次确认。不能靠要求客服复制长编码保证关联；自然确认必须绑定同人、同会话内唯一当前方案。

相同具体方案已有有效明确确认时不再追问，必须以可信来源证据与最终效果核对证明覆盖，不能仅放宽时间条件。预览、库存或关键参数变化后，原确认不得自动用于新方案。PMS 判定不可执行时说明原因并重新建议。

### 4.3 收款、入住及后续房态

- 先预订还是先收款，按实际业务与 PMS 允许动作推进；不能一律要求全款才能预订。
- 对话可主动查询 PMS 已同步流水。付款人可能不是入住人；金额、昵称相同不证明归属。
- 经核实并确认后，用真实流水引用登记收款；已被工作人员登记的流水只回读结果，不再登记。
- 未收、部分收款、未到店分别保留。申请日期或到账事件不能证明实际到店；小客服确认到店后再按 PMS 条件入住。
- 改期、续住、换房、取消预订和退房复用同一预览/确认/回执链，展示日期、库存及金额影响；失败不伪造完成。
- 退款登记、会员业务和维护等其他员工能力按实际授权和验收逐项接入；未支持要明确说明，不能泛化成主管专属。PMS 的退款事实登记不等于向支付平台实际退款，Token/权限管理也不因“员工同等能力”自动开放。

### 4.4 暂停、更正、人工接手与恢复

- 支持对话查询进度、补充信息、更正未执行方案、暂停和取消待办；取消事项不自动撤销已提交的 PMS 业务。
- 正在执行或结果未知时，先核对 PMS 结果；不得因用户催促、换会话、换 Agent 或重启重新建单。
- 用户直接在 PMS
  UI 办理后，岸岸重新读取当前事实，结束对应等待/提醒；不另建一份冲突动作。
- 有权客服临场选择其他合法方案不自动升级主管审批；长期规则修订仍由主管与四老师负责。

## 5. PMS 接口、凭据和工具约束

接口以 Green
PMS 当前 OpenAPI/源码为准，不从旧交接文件猜参数。实施时固定两仓基线及模拟契约证据。

| 用途           | 已有入口                                                                              | 接入要求                                                                                               |
| -------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 能力与权限发现 | `GET /api/v1/me`                                                                      | 读取 `propertyAccess`、`propertyCommandGrants`、`allowedActions`，与岸岸已支持工具及实际操作者授权相交 |
| 库存与业务读取 | `/api/v1/meta`、物业下的 availability/room-status、orders、members、external-payments | 遵守字段、分页、有效时点和物业范围；不要一次抓取所有资料                                               |
| 报价           | `POST /api/v1/quotes`                                                                 | READ 可用但会形成持久 Quote；不是普通 GET，也不走 Preview/Confirm                                      |
| 预览/执行      | `POST /api/v1/command-previews`、对应 preview 的 confirm                              | 使用准确 commandType、propertyId、expectedEffectHash、reason；确认不能跨执行主体复用                   |
| 结果及恢复     | commands、receipts、command-results 及 `POST /api/v1/command-results/resolve`         | 沿用 PMS 幂等、执行锁与封存原请求键的恢复协议                                                          |

所有业务写请求按 PMS 协议设置 `Idempotency-Key` 和
`X-Correlation-ID`；键由受控执行逻辑生成并持久化，不由模型任意更换。保存预览与执行各自的键、`commandId`、`receiptId`
和结果；金额采用 PMS 的整数最小单位，住宿日期使用物业业务时区与 PMS 到离语义，不能凭自然语言猜三晚的结束日期或以浮点计算资金。

网络中断后的 GET 返回
`UNKNOWN`，不证明请求未执行。先使用 PMS 已有 resolve 协议核对/封存原键，仍为 UNKNOWN 就继续等待；新尝试必须有可证明未执行的结论及重新满足的业务条件。

凭据绑定由能力包一次确定并写入包契约。可采用候选名
`GREENPMS_BASE_URL`、`GREENPMS_API_TOKEN`，目前并非已实现的 Hermes 内置变量。若插件在岸岸 Profile 内运行，可从
`/home/ubuntu/.hermes/profiles/anan/.env` 读取专用 Token，文件权限 `0600`，目录
`0700`。不复制整个 default
Profile；不写进 SOUL、Skill、源码、命令参数、日志或模型输入输出。`.env`
和同 UID 进程不构成 Agent 间强隔离；工具应只返回结果，不提供读密钥、任意 URL 或自由 HTTP 执行入口。若生产威胁模型要求对具备终端工具的 Agent 强隔离，应使用已有隔离执行边界或单独评审最小执行组件。

每次敏感读取和写入核验请求人有效授权、岸岸工具范围与 PMS 执行权限；撤权后旧会话/旧预览不能继续执行。确认逻辑使用服务端证据，不能接受模型自填
`approved=true`。群中允许交谈也不等于能批准 PMS 操作。

## 6. 持久状态与关联

复用 Agent OS
WorkItem、事件、Person 和来源引用，必要时增加最小元数据/迁移。在共同底座保存协作引用，不复制整套 PMS 订单、资金或库存库，也不把 Hermes 会话文本当作唯一执行账本。

一个客房事项关联多次查询及多个业务动作。每个动作独立绑定预览、确认、执行键与回执；订单已创建但收款登记失败时保留两者各自结果，不把整个事项重新执行。

需要表达的信息包括：来源消息/事件、请求人与确认人、Agent、范围、Person/PMS 引用、当前待办、规则与方案版本、执行状态、失败原因、人工接手和最后回执。

状态语义至少覆盖：待补信息、待确认、执行中、已完成、确定未执行、结果待核对、暂停、取消/人工接手。映射到现有任务状态/阶段字段，不为了命名再造平行状态系统。

执行前持久化意图并领取唯一执行权；外部调用不占用长数据库事务。进程在“PMS 成功、本地未记回执”时崩溃，恢复先查 PMS 原请求结果。

## 7. 后续触发与协作流程

### 7.1 Green PMS 新收款

企业微信收款 → PMS worker 同步保存 → `pms.payments.v1` → Agent
OS 接收/持久化 → 岸岸原有办理流程。PMS 是收款事件来源；岸岸不另做企微流水同步器。当前可复用
`GET /api/v1/external-payment-events`，不得把“有 feed”写成“真实推送已上线”。先用现有 feed 实现消费者，后续有已验收投递才接通知；无需为此先改 PMS
CI、生产部署或新建消息中间件。

- 按现有 `schemaVersion`、`eventId`、物业和配置的来源实例隔离去重；`nextCursor`
  原样保存，不按 JS 数字处理。
- 成功持久化事件及对应任务后才推进检查点；通知失败可以恢复，不能因 cursor 已前进而丢任务。
- 首次启用冻结基线/启用边界并追赶期间新增，历史流水及历史关联不批量创建新催办。
- `DISCOVERED` 先判断是否确需办理；`MATCHED` 回读并更新已有事项，不能当第二笔新收款。
- 已有预订优先核对，缺订房资料则问询；收款不是自动建单或入住的指令。
- 事件只唤醒事项，不冒充小客服发言或批准；后续写入仍按各自确认门禁执行。每笔 RECORD_COLLECTION 必须有有权人对具体订单、流水和金额的明确确认；已有完整明确交办可计作该次确认，

  但岗位/长期授权、到账事件或模型推断均不能替代，不强迫重复同一决定。

群内问询须核验岸岸专属 Bot 的真实主动消息能力、目标工作群与有效发送条件。会话回复成功不能证明事件发生后可以主动发群消息；能力不足时保存待联系状态并说明接线缺口，不静默换用 default、四老师或另一渠道身份。

### 7.2 飞书入住申请

飞书表单 →
Base 新增/修订 → 现有 Workflow/Bridge 的统一接收点 → 申请案例 → 四老师与岸岸各自职责。申请来源属于飞书，Green
PMS 不负责发起或轮询申请事件。事件只携带必要的来源引用和版本线索，接收端按固定授权读取记录；不让事件指定任意 API 地址。

- 保留原四老师业务，先核对真实通知入口和消费行为；新增岸岸分派，不能让两个独立扫描器同时办理同一申请。
- 以 Base/table/record 来源引用及可靠版本/变更标识去重；版本字段由飞书实际能力决定，不能凭空假设。
- 四老师接收运营职责所需内容，岸岸接收订房必需内容；申请提交不证明已付款、已订房或实际入住。
- 为申请字段到 PMS 客户/住客及订单字段建立最小映射，沿用原表单；缺失或冲突只询问当前动作所需信息。经确认后由同一受控工具写入 PMS 的既有字段，不把申请全文、证件附件或全部个人资料复制到群聊和事项日志。
- 同一申请修订继续原案例；已完成订单不自动按表单新内容改房态，重新核对必要业务影响。
- 申请、收款和对话可以任意先后到达。只有可靠来源引用或有效人工确认才能关联；同名、金额相同不能合并。同一个人多次住宿保留独立事项，付款人与入住人也可以不同。
- 订单允许没有本次申请，老客无需为系统关联重新填表；申请也可以尚未付款，不制造全量人工补档任务。
