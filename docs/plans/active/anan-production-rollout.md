### 业务事件的接收与办理分工

既有契约为 Green PMS worker → Agent OS Sidecar 接收入口 → 持久事件和 WorkItem
→ 岸岸沟通办理，不是 PMS 直接向岸岸聊天或调用模型。

固定入口为
`POST /api/v1/ingress/pms/events`。Sidecar 校验签名、来源与物业、去重，并在事务提交后返回持久接收回执。接收回执不表示已通知到人，更不表示已登记收款。

岸岸按原事项查询事实、提出建议、与有权人员确认具体流水、金额和订单，再执行及核对业务回执。

主流程是 PMS 主动投递；feed 用于首次事件头基线及漏失补拉，不能把轮询当作主动通知，也不让岸岸重复同步企微流水。接手时签名接收只挂在本地模拟监听器；本批已增加独立生产 loopback
listener，并接入 Sidecar 原有 Run 生命周期，默认关闭。提交后的内部即时提示已完成联合模拟；恢复扫描及岸岸主动联系仍待接线，生产部署及真实验收均未完成。

反向代理必须保留原始请求体和签名头，以 HTTP/1.1 转发至固定端口，并设置
`Host: 127.0.0.1:<port>`；不能通过放宽本地 HTTP 解析规则接受任意 Host。

Sidecar 到岸岸的即时唤醒优先核查官方 Generic
webhook。它位于 PMS 接收与持久事务之后，不能替代前面的 Sidecar 入口。

候选仅传既有 WorkItem 引用，通过固定只读工具集读取当前待办，不携带原始流水、申请正文或人类批准。

官方入口的 202 和去重结果均不证明模型回合完成，去重记录重启后会丢失；共享 WorkItem 仍是恢复依据。

必须核验独立密钥、显式 loopback、固定模板、实际只读工具集合以及网关命令边界，才能实施该接线。内部 webhook 来源不是企微人员身份，不能进入人类确认或 PMS 写入路径。通知对象与真实送达另按原渠道契约处理。

当前实现先返回已提交事件的原持久 ACK，再以最多 2 秒发送内部提示；正文只有版本与 WorkItem
UUID。Sidecar 签名发送、官方 HTTP handler、入站 hook、只读工具及真实 Unix
broker 回读已在隔离 PostgreSQL 联合模拟中通过。提示失败不更改接收回执、不标记已通知；重启后仍须按共享事项恢复。该联合模拟替代了安装与隔离前提，不能和另一场 Linux 隔离模拟拼称为生产全链验收。

## 工具隔离核查与实施顺序

只读核对官方干净 `v2026.9.21` 源码（`d337b736aa1e8ebecfab043842d13e4a2d2f48a3`）：

- terminal、文件工具与 execute_code 共用官方 terminal
  backend；非 local 初始化失败不得回退 local。
- Docker 使用只读技能/缓存挂载；SSH 会回同步技能文件。首选官方 Docker，关闭宿主 cwd 自动挂载，不挂载 Profile、私有凭据、宿主 socket 或 Docker
  socket。
- Skill 环境声明会转发已配置环境变量，因此三个 Token 不进入 Gateway 环境、Skill
  secrets 或凭据挂载目录。Profile 外私有文件只是其中一道条件。
- cron 脚本使用宿主 subprocess，browser_use
  Python 也有独立宿主执行路径；它们不随 terminal
  backend 自动隔离。首批限定建议已向负责人提出，批准前不改变既有能力。
- 隔离探针覆盖文件读取、Python、环境变量和 Skill 凭据声明；官方进程实际加载、失效拒绝和可调用工具集合须单独验证。单元模拟不能替代 Linux 隔离验收。

补充核查：官方 `browser_cdp` 在公开页面仍会转交 `DOM.setFileInputFiles`
的任意文件路径；离线记录型传输模拟已确认该调用会被转交，但未启动浏览器或读取文件。普通浏览器运行在宿主时，不能以 terminal
Docker 或文件名 `.env`
证明私有凭据不可达。优先沿官方 CDP 接入隔离浏览器并核验实际文件系统、挂载及失败行为；接线完成前不得把当前候选策略判作完整隔离通过，也不自动关闭全部浏览器能力。

候选实现使用官方内建浏览器工具连接独立 Docker 浏览器的固定 loopback
CDP 端口。root 所有的 managed overlay 在 `qintopia_pms_isolation.browser`
中固定容器名、镜像摘要和
`cdp_url`；插件同时校验官方实际解析结果、Docker 运行状态和端口映射。

浏览器不挂载宿主文件或 socket，不注入额外环境变量；拒绝缓存中的宿主浏览器会话、临时 CDP 改道、云端失败回退及扩展控制改道。失联或配置漂移使业务调用拒绝，而不是退回宿主浏览器。

这是默认关闭的实现候选，尚未选定生产浏览器镜像或安装容器。一次性 Linux Gateway 的完整
`production.require()` 已通过模拟验证；生产运行用户、真实配置及页面行为仍须验收。

受管配置还须校验完整父目录链：每层为 root 所有、不可被其他用户改写的真实目录，最后的配置文件须为普通文件，禁止符号链接。

由于私有 webhook 密钥使用该配置内的 literal，受管目录和文件不允许其他用户读取。仅检查最后两层的所有者不足以防止可写父目录替换整个策略目录。

固定摘要 Chromium 容器的实际挂载、运行身份、文件可见性及 CDP 发现模拟已通过。

后续完整 Linux 模拟发现当前官方核心浏览器辅助函数读取 Profile 原始配置，不应用受管覆盖。因此安装须只对齐已审阅的浏览器字段，保留其他 Profile 内容。

插件同时校验受管、合并及原始配置，单独正确的受管文件不能通过预检。未使用 Playwright 或进行页面自动操作。

实施次序：明确 live 租户与共享配置入口 → 插件和可信会话接线 → 固定官方工具隔离 →
Sidecar 生产事件接收与持久唤醒 → 岸岸沟通、申请和欢迎交接及规则提醒 → 包级与隔离 PostgreSQL 联合验证 → 固定产物与安装/回退预检 → 负责人发起真实验收。

生产安装、权限配置与新隔离运行条件先形成可审阅步骤；不在调查阶段注入凭据或修改服务器。新增 CI/发布门禁仍按九项原则专项评审，普通开发授权不包含此项。

独立审阅补充：官方 MCP stdio 运行在宿主，不继承 terminal

独立复核进一步确认：`run_profile_reconcile.py`
会在配置变化后自动连接 MCP，可能先启动宿主进程、后在下一次 `require()`
被拒绝；未注册工具的已启动进程也不在工具注册表中。因此一次 `ExecStartPre`
检查本身不够，须固定 native/portable 配置及插件来源，并核实真实 Gateway 的加载时序。官方插件加载失败会继续运行，生产启动接线仍未完成；现有 MCP 负例只证明调用时拒绝。

继续核对固定官方源码后，启动方案还须处理三类既有行为：

- MCP
  discovery 先于普通插件 hook 注册；预先在另一进程加载插件不能证明真实 Gateway 的状态。
- 强制插件 reload 会先卸载 hook，随后重新发现；配置型 shell
  hooks 可以在宿主执行，不能遗漏这条执行路径。
- 官方恢复会接纳仍存活且 PID/启动时间吻合的宿主进程；不能靠删除 checkpoint 或只停止 Gateway 声称它们已退出。

受管覆盖不是 OS 只读边界，空 `mcp_servers`
字典也不会抹去用户配置的 MCP。因此专项激活方案需分别证明无凭据静态预检、真实同进程的启动顺序、配置与插件来源持续受保护，同时保留会话、记忆、日志和任务状态的必要写入。

当前 user
service 的同 UID 路径替换、强制 reload 与运行中宿主进程尚无完整 Linux 证据。现有专项启动器/drop-in 草案仅作范围评估，尚不构成已选定、可实施的安全方案。

不在普通发布流程中自动安装它；具体部署契约及功能影响完成验证和九项原则评审后才请求专项批准。

### 切换顺序

1. 运行解析器、Agent 管理、部署 runner/smoke 测试，再运行
   `pnpm check:pr:auto`。生产接线另测越权、重复确认、未知结果、重启恢复和共享数据库迁移兼容。
2. 检查最新提交 CI 与 reviewer，修复有效问题；CI 通过不等于允许自动合并或发布。
3. 部署前记录固定 SHA、校验清单、原发布指针和服务入口；服务器本地一致性备份。不覆盖 Profile 模型、通道、凭据、任务、会话或记忆，不热改源码。
4. 普通发布使用现有 runner 发布/回退流程，岸岸仍使用原核心入口。等待当前任务结束再重启；超时暂缓。记录共享组件影响，不能声称只影响岸岸。
5. 回退必须使用支持该 target 的已验证 runner 和先前不可变产物；旧 runner 不认识新 target 时不能直接提交回退请求。首次接管前先验证这一兼容条件。后续插件激活需单独保留旧入口并演练恢复；不回滚实时业务数据。
6. 用户发起真实查询及一笔已授权办理，核对 PMS 事实、事项与原会话回执。未提供合适业务事项时保留写入验收未完成，不自行虚构订单或发送测试消息。

### 生产入口核查补充

`Store::local` 限定模拟租户与测试库，`Store::begin` 和 `authorize_current`
也要求模拟模式。

因此生产接入须增加明确绑定真实租户的入口，沿用当前 Person、范围和确认校验；不能使用 LOCAL_ENABLE、模拟租户或模拟数据冒充上线。

现有岸岸未显式配置工具白名单。默认保留已有通用执行工具，优先复用官方隔离执行能力，验证凭据不可达性后才启用生产凭据。

缩减为 PMS 业务工具白名单仅作为负责人主动选择的替代方案，不作为继续开发的前置确认；不自行删除已有工具能力。两条路线均不改变业务授权与人类确认。

### 凭据隔离接线

官方 v2026.9.21 的隔离进程探针使用虚构 Token，确认 Skill 的环境变量声明可以转发
`GREENPMS_API_TOKEN`、`QINTOPIA_FOUNDATION_TOKEN` 与
`QINTOPIA_FOUNDATION_HOST_TOKEN`。不能只切换远端 terminal 后继续使用这些环境变量。

PMS 插件增加显式私有凭据文件输入：文件位于 Profile 外、仅当前运行用户可读写，拒绝软链接、硬链接、可被其他用户改写的父目录和环境变量凭据副本。本地模拟仍兼容原环境变量方式；

文件输入不打开生产模式。正式部署还须验证远端工具不可访问该路径、配置不可被模型修改及所有有效工具路径。

真实人员绑定仍待负责人指定；只读 PMS 清单查询不建立授权、不创建 Token、不改业务数据。
