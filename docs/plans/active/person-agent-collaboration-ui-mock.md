## ① 首页：全社区谁和谁合作

**全社区组织与智能体协作**

搜索：`输入人员、岗位、智能体或群名称……`

筛选：`全部工作范围 ▾`　`全部智能体 ▾`　`当前有效关系 ▾`

**关系图（示意）**

```text
公司负责人 ───────────────→ default agent
      │
      └── 社区负责人（刘珊） ──→ 四老师
               │
               ├── 一栋舍长 ──→ 二花 ──→ 一栋群聊 / 一栋私聊
               ├── 二栋舍长 ──→ 二花 ──→ 二栋群聊 / 二栋私聊
               ├── 三栋舍长 ──→ 二花 ──→ 三栋群聊 / 三栋私聊
               ├── 小管家 ────→ 二花、客房智能体
               └── 活动负责人 ─→ 小满
```

关系图可以按人员、智能体、范围或职责查看。它不是固定组织层级；新增人员、智能体、群或关系后自动更新。

**横向支持关系（新增讨论）**

```text
技术负责人（目前：弦默）
    ├── 为业务责任人提供智能体使用与训练支持
    └── 为所负责的智能体提供技术支持
            二花 / 小满 / 四老师 / default agent / 客房智能体
```

这类岗位使用同一套框架，通过“技术支持”职责连接多个智能体和责任人，不单列一套特权身份。岗位名称暂用“技术负责人”，可调整。

业务问题找业务负责人，工具故障、知识未保存、训练效果异常等找技术支持。具体可维护的智能体和可执行的技术动作另行明确；支持关系本身不授予业务裁定、全量私密资料读取、生产部署或权限扩大能力。

| ---------- | -------------- | ------------------- | ---------------- | ---------------------------------------- | ------------ |
| 人员甲     | 一栋舍长       | 一栋 · 一栋居民群   | 二花             | 补充楼栋信息、指导居民服务、审核楼栋内容 | `查看与调整` |
| 人员乙     | 二栋舍长       | 二栋 · 二栋居民群   | 二花             | 补充楼栋信息、指导居民服务、审核楼栋内容 | `查看与调整` |
| 小管家     | 小管家         | 社区 / 客房相关范围 | 二花、客房智能体 | 客房协作、日常协调                       | `查看与调整` |
| 活动负责人 | 活动运营负责人 | 活动运营范围        | 小满             | 活动运营协作                             | `查看与调整` |

`＋ 添加人员`　`＋ 添加智能体`　`＋ 添加工作范围`　`管理职责`　`查看变更记录`

同一个人可以担任多个岗位；不同岗位可以与同一个智能体合作。

**谁可以设置：**
公司负责人可以设置整个组织框架；社区负责人可以设置社区范围内的人员、职责和合作关系。具体设置动作仍受工作范围限制。

**范围会变化：**
当前群聊和私聊可以作为初始配置；群可以新增、停用或重新绑定，私聊对象和可讨论内容也可以调整。历史关系保留，只有当前有效关系参与新的协作判断。

朋友、家人、守护者、值日等参与关系可以另行记录，不是互斥的人员类型，也不会自动带来训练或审批权。入群与实际入住分别记录。

## ② 设置一条合作关系：授权边界怎么设

**页面：人员甲 · 一栋舍长 ↔ 二花**

`合作对象与范围`　`授权边界`　`合作习惯`　`交接记录`

### 第一步：选择人、智能体和范围

| 设置项       | 界面示例                       | 选择方式                                 |
| ------------ | ------------------------------ | ---------------------------------------- |
| 人员         | 人员甲                         | 姓名/昵称搜索，核对后选择已有人员        |
| 岗位         | 一栋舍长                       | 选择或创建岗位；岗位称号本身不授予权限   |
| 合作智能体   | 二花                           | 从 runtime 已登记清单搜索选择            |
| 负责领域     | 一栋共同生活与运营             | 选择职责方案，允许自然语言补充           |
| 群聊         | 一栋居民群                     | 从群清单搜索、多选                       |
| 私聊接待方式 | 二花开放接待主动联系的人       | 不把在住、过往或预先登记作为普通交流前提 |
| 主动联系约定 | 居民服务、问题跟进、活动交流等 | 按职责、联系意愿和合作约定动态选择对象   |
| 私聊内容     | 本栋居民服务 / 内部审核与汇报  | 分别说明不同对象可讨论的内容             |
| 有效期       | 开始日期 → 至离任              | 可设临时代理的结束日期                   |

普通咨询和公开信息交流不要求提前逐个登记或审批。需要修改正式知识、训练智能体、作出业务决定或提供受限信息时，再核验适用身份和权限；一个人在私聊里指导二花更新本栋知识，影响范围仍是一栋。能聊天不等于取得训练或管理权限。

“成员范围”会随已确认的成员关系变化，不等于永远绑定曾经进群的人。入群不证明实际入住，也不自动授予训练权。对象无法核验时可解释和引导核对，不能披露只对成员开放的内容。

### 私聊分开设置接待、主动联系与信息使用

| 设置项   | 二花的合作方式                                                                 |
| -------- | ------------------------------------------------------------------------------ |
| 开放接待 | 主动联系的人可以进行普通咨询、交流和提供信息，不限于在住或过往人员             |
| 持续交流 | 在服务职责内与已建立联系的人自然交流，不逐句话审批                             |
| 主动联系 | 根据服务目的、合作约定和对方的联系意愿动态选择；对方不希望继续联系时尊重其选择 |
| 信息使用 | 公开内容正常交流，受限内容核对对象；新信息整理确认后再作为正式依据             |

收到私聊的接待规则、主动发送的授权和信息可见性分别执行。开放接待不自动启动批量私聊，不扩大到其他智能体，也不表示旧渠道限制已经完成调整。

### 每个任务再选择本次联系对象

| 设置位置 | 字段                   | 作用                                                 |
| -------- | ---------------------- | ---------------------------------------------------- |
| 合作关系 | 服务职责与主动联系边界 | 定义可以开展哪些合作和交流，人员关系可以在服务中发展 |
| 具体任务 | 本次联系哪些人         | 根据本次目的，在已授权范围内选择实际接收人           |
| 合作习惯 | 这类任务默认联系哪些人 | 重复任务沿用已确认约定，不要求每次重新设置           |

**入住人员范围选项：**

| 选项         | 含义                                       |
| ------------ | ------------------------------------------ |
| 在住         | 当前实际住在所选楼栋的人                   |
| 过往         | 曾实际住过所选楼栋，目前不在该楼栋住宿的人 |
| 全部入住人员 | 在住与过往的合集，不是通讯录中的所有人     |

范围依据可靠的实际住宿记录和已确认人员关联判断。资料不明的人保留待核对，不因为查不到当前入住就归为过往；人在群里不等于在住。再次入住本栋的人按当前在住判断，不能因也有历史住宿而重复联系。

**任务示例：**

| 本次要做什么       | 本次联系对象                     |
| ------------------ | -------------------------------- |
| 本栋临时停水通知   | 在住人员                         |
| 离住体验回访       | 过往人员，可再限定离住时间       |
| 本栋老友活动邀请   | 全部入住人员，或其中选定的一部分 |
| 跟进某人提出的问题 | 指定人员                         |

这些是用法示例，不是预先授权的发送任务。责任人可以用自然语言提出对象，二花整理为清楚的任务范围；“通知大家”等对象不明的表述，由二花针对本次任务澄清。日常任务可在合作启动时约定默认对象，执行时按当前有效身份、授权和该约定核对。

允许服务某个人，不等于可以主动给他发任何内容。主动私聊仍需相应发布授权，并检查内容对该对象是否可见。例如，过往住客可以在适用授权下收到活动邀请，但不能因此获得仅向在住人员开放的门禁、钥匙等信息。

在住、过往和全部入住人员用于相应通知、回访等任务筛选，不作为日常私聊的封闭名单。未入住的咨询者、感兴趣的朋友等也可以与二花交流；任务需要时可以选择其他适用对象，不把他们强行归入入住人员分类。

聊天中留下的是与服务有关的知识线索、待处理问题及对方愿意提供和用于相应服务的偏好。二花应说明用途、允许纠正和停止相关联系；不会因为某人愿意聊天，就把整段私聊或其中的个人烦恼公开给舍长或居民。待确认的公共生活知识与个人信息分开处理。

### 第二步：选择职责方案，再按需展开权限

**职责方案：** `舍长 · 本栋自治与居民服务 ▾`

方案由有授权资格的管理者维护，任职时预填常用权限；不要求为厨房、书架、洗衣机分别设置。每类权限可选择“可自主决定”“可提议，交给指定负责人确认”“未授予”。

| 这个人可以决定什么         | 一栋舍长示例     | 说明                                                   |
| -------------------------- | ---------------- | ------------------------------------------------------ |
| 确认、修订本栋知识         | 可自主决定       | 居民提供的信息由负责人吸纳、纠正、否定或转成待处理事项 |
| 训练二花的本栋服务方式     | 可自主决定       | 本栋语气、文案、提醒、工作习惯                         |
| 调整本栋运营规则           | 可自主决定       | 在社区文化和责任边界内自治，不逐条报总负责人           |
| 审核本栋发布内容           | 可自主决定       | 审核内容不等于已经发送                                 |
| 授权二花主动发布           | 展开选择发布方式 | 可以选逐次确认或在已批准约定下持续发布；不等于任意群发 |
| 指定本栋业务确认人         | 可自主决定       | 为本栋具体职责指定人，不自动任命全局管理员             |
| 调整组织授权、扩大他人范围 | 本示例未授予     | 由拥有相应授权管理权的人设置                           |

“提供信息”是参与入口，普通居民也能使用；进入待确认清单不等于取得上述管理权限。

自然语言用于说明工作职责、提出调整；系统整理成清楚的范围和权限后，由有权者确认。智能体不能把一段描述直接变成新增权限，也不能凭“未被禁止”放开工具执行。

### 第三步：区分人能决定什么、二花能执行什么

| 二花的工作                         | 界面如何呈现                                                                     |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| 收集信息、提出问题、整理线索与反馈 | 在允许接入的会话中自动分类保存；仅需业务决定的事项进入待办，不把全部信息转为待审 |
| 回答问题                           | 使用当前有效、对当前对象可见的知识；待审知识不当成正式事实                       |
| 汇报、提醒、普通问候               | 由启动合作时形成的约定决定时间和方式，执行还需适用的发布授权                     |
| 发布需要审核的内容                 | 按适用的逐次审核或持续授权执行，核对对象和内容范围                               |
| 正式欢迎、正式入账等业务动作       | 同时检查各自业务条件和实际可用能力，不能由训练指令绕过                           |

MVP 中，人有某项决定权，不等于智能体已经具备对应工具。例如，舍长有权指定基金确认人，并不表示基金台账功能已实现。

### 第四步：显示共同约束及可见范围

**继承的约束：** `秦托邦社区文化`　`社区责任边界`　`隐私与业务要求`

这些规则应来自社区已经确认的内容，可查看来源和版本；不能由模型临时编造所谓“社区原则”。一栋职责配置不能覆盖上层边界。

**知识供谁使用：** `服务范围内的成员`　`仅负责人和指定协作人`　`可对外公开`

这组可见性标签是界面建议，可按知识类别预设并在必要时调整。能私聊某人不等于能把所有资料给他；钥匙、网络访问等信息也需按适用对象和当前有效性提供，草图不保存真实内容。

新主题在已有职责和范围内即可处理。如果“共享书架”后来加入一栋生活，并不新增一个权限按钮。范围明确的日常事务正常进行；真正越出授权、违反现有规则或存在无法解决的冲突时，才暂停受影响动作并说明原因。

### 谁能授予和改变边界

| 设置人     | 可以管理什么                                                         |
| ---------- | -------------------------------------------------------------------- |
| 公司负责人 | 整个组织框架，包括授权管理范围                                       |
| 社区负责人 | 公司负责人已赋予其管理权的社区范围                                   |
| 一栋舍长   | 已授权的本栋自治、合作习惯及业务确认人，不自动扩展其他楼栋或全局权限 |
| 技术负责人 | 获授权的技术支持范围；技术支持关系本身不授予组织管理权               |

有权执行某动作，与有权把该权限授予别人分开。只能在自己的授权管理范围内任命、代理或转授；界面连线和聊天指令都使用同一规则，不能靠改岗位名称、改群标签或新增连线扩大范围。

多人共同负责时，按事项类别指定确认人；有实质冲突时交有管辖权的负责人处理，不能简单采用最后发言者或把多个岗位权限拼成更大权限。

### 保存前：预览实际效果

> 人员甲与二花合作负责一栋共同生活与运营。
>
> 他能确认一栋知识、训练本栋服务、调整本栋规则、审核内容并指定本栋业务确认人。群聊、私聊对象及发布方式使用本页所选配置；新增生活主题不需要另设权限。
>
> 二花只能向适用对象提供可见知识。公司和社区的共同边界、正式欢迎等业务条件继续生效。
>
> 离任或授权撤销后，后续动作使用新的有效关系，旧权限不再执行；保留历史记录。

`返回调整`　`确认保存`　`保存后准备合作启动`

保存授权后，由智能体引导责任人商定工作节点和习惯。未完成某项习惯不阻止其他已授权工作；尚无发布约定或权限时，不自行开始自动发送。

## ③ 换个角度：从二花看“我该听谁的、找谁”

**智能体：二花**

`合作人员`　`服务范围`　`可使用的信息`

| 当前服务范围 | 谁能指导我        | 可以指导什么       | 需要协助或审核时找谁     |
| ------------ | ----------------- | ------------------ | ------------------------ |
| 一栋居民群   | 人员甲 · 一栋舍长 | 一栋信息与居民服务 | 人员甲，按已配置职责处理 |
| 二栋居民群   | 人员乙 · 二栋舍长 | 二栋信息与居民服务 | 人员乙，按已配置职责处理 |
| 社区公共群   | 待设置            | 待设置             | 显示“尚未指定负责人”     |

这是同一套设置的另一种查看方式，不需要在二花这里再配一遍。

**工作范围示例：**

| 工作范围 | 关联的群                       | 信息如何使用             |
| -------- | ------------------------------ | ------------------------ |
| 一栋     | 一栋居民群；可按需要关联其他群 | 一栋信息用于服务一栋居民 |
| 二栋     | 二栋居民群                     | 二栋信息用于服务二栋居民 |

一个工作范围可以关联多个群；群也可能承担多类事务。具体事项同时看“发生在哪个范围”和“属于谁的职责”，不能只凭群名称找人。

## ④ 实际合作：舍长说了一件事，二花怎么用

**虚构场景：人员甲告诉二花**

> 一栋公共厨房这周暂停使用，周一恢复。请记下来，居民问到时告诉他们。

二花根据前面的设置识别：这是有权补充一栋信息的人，明确要求记录一栋的设施安排。

### 按需查看临时设施状态

这是有时效的运营状态，不是长期知识条目。系统自动保存供跨对话查询，UI 在设施状态或相关事项中按需展示；不要求工作人员为零散事件建卡或维护字段。下面表示可查看的信息，不代表每条聊天都生成一张卡片。

| 项目       | 展示内容                                         |
| ---------- | ------------------------------------------------ |
| 信息       | 一栋公共厨房临时暂停使用                         |
| 提供人     | 人员甲 · 一栋舍长                                |
| 供谁使用   | 二花                                             |
| 适用范围   | 一栋                                             |
| 可告知对象 | 一栋居民                                         |
| 有效时间   | 本周暂停，计划周一恢复；保存时记为具体日期       |
| 用途       | 居民问到时回答                                   |
| 主动群发   | 本次未要求；如需通知，另按发布权限与审核要求处理 |

`查看来源说明`　`纠正信息`　`标记失效`

**之后会发生什么：**

- 一栋居民问“厨房能用吗？”：二花根据这条仍有效的信息回答。
- 二栋居民问同样的问题：二花查二栋的信息，不套用一栋的安排。
- 到了恢复日期：不把已过期安排继续当作当前依据；计划恢复不等于实际恢复，必要时说明最新状态尚未确认。
- 舍长提供的是只供内部处理的信息：不会因为二花知道了，就直接告诉居民。
- 新信息与已有记录冲突：交给对应职责的负责人核对，不默认最后一句话覆盖一切。

普通居民提供的是状态线索，保留来源而非直接成为管理决定；已授权负责人的明确安排使用其有效权限保存。已有证据可以自动解决的修订由服务处理，不为可选信息缺失追加人工核实任务。

附近玩乐推荐、社区意见、个人记忆与正式知识的分类及主动收集框架，统一见[业务模型第 11 节](../../agent-os/community-business-model.md#11-二花通过互动收集信息与积累社区记忆)。相关视图仍是设计，不表示已经交付。

## ⑤ 入住欢迎使用同一套关系

2026-09-22—23 本批页面验收纠偏：负责人明确欢迎只是舍长在已获授权内决定的单项业务，不设置独立导航分类、专页或配置表单。原组织架构页面面向组织管理者，保留为任职与授权入口；舍长通过二花日常对话确定约定、查看具体内容并按需批准，不另建记忆、规则和流程维护控制台。开发验收工具不进入业务导航。下面的设置项描述业务语义，不是要求新增页面。

2026-09-22 负责人确认：社区负责人在管理授权范围内设置舍长的决定权；舍长在有效权限内自行设定文案形式、单次转审、持续默认转审或获准的直接发送。实际业务标准见[共同契约 §6.4](unified-person-welcome-v1-contract.md#社区授权舍长设置与具体审批负责人确认2026-09-22)。

欢迎由岸岸（客房智能体暂定名）编排、阿靓制作卡片，二花传递审核并转发。它们消费统一的规则、事实与任务，不能把这份合作设置变成二花独立的制卡流程。

**通过事项对话表达的本栋约定：**

| 设置项   | 表达方式                                                                 |
| -------- | ------------------------------------------------------------------------ |
| 文案形式 | 本栋模板、语气和允许的变化范围；仍受个人资料许可限制                     |
| 审核方式 | 做好直接发 / 先给适用负责人审核                                          |
| 适用事项 | 仅本次欢迎 / 本栋后续欢迎的默认设置                                      |
| 持续时间 | 明确起止时间，或持续到有权调整/任职及授权失效                            |
| 权限解释 | 显示可自主设置、需指定人确认或未获相应权限；不能用欢迎设置提升人的决定权 |

“这一位先给我看”只设置本次要求，不改默认；“接下来一个月都先给我看”保存期间默认，每次内容仍分别审核。已有默认先审时，拥有相应自主权限者也可明确只让本次直接发；不能绕过上层强制确认。

舍长拥有自主权而要求二花每次转给自己审核，是自主选择的运营习惯，不是把舍长自己的权限设成“需指定人确认”并让他自审。现有工作台三态权限与任期配置属于已实现的合成配置；欢迎设置的服务、独立有效期和真实消费者接线仍待实现。

**仅在适用规则要求审核时，二花出现以下待办：**

>
> **对应范围：** 一栋居民群
>
> **审核人：** 人员甲 · 一栋舍长
>
> **为什么找他：** 他在统一设置中负责一栋群发布内容审核。

`查看卡片与文案`　`查看审核状态`　`查看负责人职责`

这里处理“本次具体内容版本是否通过”，不再出现“请重新设置一栋舍长”的表单。有效默认或本次设置允许直接发时，走二花转发待办，不额外生成逐次审核任务。选择审核人、保存转审规则、批准一份内容分别留证。

### 普通问候：合作习惯示例，不是必填权限表

下面是二花与舍长启动合作时可以讨论的内容，不要求管理员预先逐行填写。界面提供简短建议和常用选项，也支持自然语言输入；二花整理后请舍长确认。未来增加一种生活场景，不增加一套人员权限。

| 设置项                               | 设置方式                                               |
| ------------------------------------ | ------------------------------------------------------ |
| 短住者或资料不完善者入群，如何打招呼 | 由本栋舍长与二花商定                                   |
| 每次入群是否问候、采用什么文案       | 按本栋沟通确定的偏好执行，不交总负责人逐条审批         |
| 是否必须先有申请或 PMS 入住资料      | 普通问候不要求；不编造缺失的个人背景                   |
| 是否因此可以制卡或正式欢迎           | 不可以；正式流程仍检查申请、住宿、成员、审核与发布权限 |
| 已问候后又满足正式欢迎条件           | 协调问候、介绍与正式欢迎，避免接连重复打扰             |

普通问候不是“资料不齐的正式欢迎”。正式流程仍按社区和楼栋分别判断条件，条件齐备即发送，不固定等待一小时。

未设普通问候习惯，不阻塞知识收集、已授权答疑和其他工作。二花主动引导舍长确定；尚无适用约定或发布授权时，不自行启用自动入群问候。合作习惯不能放宽正式欢迎的业务条件。

**舍长换人时：**
在统一任职设置中办理交接，相关流程查到新的负责人。旧人的权限到期或撤销，新人是否有权处理由新任职决定；不会把旧人的历史审核改成新人批准。

## ⑦ 合作启动：智能体引导人建立习惯

框架已有授权后，智能体主动说明“我能与你一起负责什么”，展示当前有效知识和待办，再引导责任人确定工作重点、汇报节点、提醒方式及确认人。先利用已有材料，不要求新责任人从零填写长表。

| 阶段         | 智能体如何帮助责任人                                   |
| ------------ | ------------------------------------------------------ |
| 刚接手       | 介绍已有工作、自己的能力与限制，提出少量具体建议供调整 |
| 建立合作     | 通过对话确定工作习惯；整理成合作约定，交责任人确认     |
| 日常合作     | 收集信息、汇总待审内容，按约定找人；缺少信息时主动补问 |
| 遇到技术困难 | 给业务责任人清楚的说明，并按技术支持关系转交           |
| 换人或代理   | 核对新的有效权限，介绍历史状态，再和新人确定合作方式   |

汇报频率和普通问候偏好由具体责任人与智能体确定，本草图不统一指定时间。合作约定只能细化已有权限，不能靠一次对话扩大上层授权。
