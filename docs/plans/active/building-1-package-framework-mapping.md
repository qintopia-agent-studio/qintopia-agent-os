# 一栋需求包 → Agent OS 框架映射（讨论稿）

日期：2026-09-10。状态：讨论稿，未导入、未启用、未修改 runtime。

这份材料把一栋舍长的投喂包放入“人—智能体—工作范围—职责—知识”的通用框架。它不是第二份接口契约，也不把示例人物或群名直接当成生产配置。

## 1. 一栋需求包包含什么

| 投喂包内容               | 框架中的含义                           | 由谁确认                         | 二花如何使用                       |
| ------------------------ | -------------------------------------- | -------------------------------- | ---------------------------------- |
| 一栋文化与项目知识库     | 一栋范围内的稳定文化和生活背景         | 一栋舍长；不能违反社区文化       | 回答和引导居民时参考               |
| 一栋当前生效规则知识库   | 一栋当前执行的规则                     | 一栋舍长或其指定确认人           | 只使用当前有效版本                 |
| 动态事实表               | 会变化的事实：值日、物资、基金、房间等 | 对应事实负责人                   | 先查最新状态，不把旧记录当当前规则 |
| 事件与基金记录模板       | 需要跟进的事件和待确认记录             | 对应负责人                       | 建卡、汇报、跟进，不直接编造结论   |
| 二花工作 SOP 与标准      | 智能体的通用工作方法                   | Agent OS 共同能力 + 一栋合作约定 | 提问、记录、提醒、汇报、升级       |
| 边界、升级与隐私规则     | 社区底线和本栋处理边界                 | 社区负责人 / 适用负责人          | 超范围、冲突或敏感事项交真人       |
| 常见场景标准话术         | 语言示范，不是权限或事实               | 作为示例审核                     | 参考语气，不逐字覆盖当前规则       |
| 后台清单、验收题、群口令 | 配置和测试材料                         | 运营人员                         | 不作为居民知识直接回答             |

## 2. 四层关系

```text
社区共同原则
    ↓ 约束所有楼栋和所有智能体
一栋自治规则与一栋当前知识
    ↓ 在一栋范围内服务居民
二花的工作方法
    ↓ 通过合作约定连接具体责任人
一栋舍长、守护者、基金确认人等自然人
```

社区原则负责“不能做什么”；一栋规则负责“本栋怎么生活”；合作约定负责“二花怎样与责任人一起工作”；动态事实负责“现在是什么状态”。四者不能混成一份最高优先级提示词。

## 3. 谁可以提供信息，什么会成为正式依据

所有一栋居民都可以提供信息，包括 Wi‑Fi、钥匙位置、公共物资、设施问题和临时安排。提供信息只产生一条可追踪记录，不自动改变当前知识。

```text
居民提供
  → 二花记录来源、范围、时间和内容
  → 汇总到舍长的待确认清单
  → 舍长确认、修改、否定、转为问题或标记过期
  → 进入一栋当前知识 / 动态事实 / 处理事项
```

普通生活知识也走这条路径。紧急安全问题可以立即提醒相关真人；“立即提醒”表示升级速度，不表示二花可以跳过确认自行宣布长期规则。已确认的信息要带适用范围和有效时间，过期后不再作为当前依据。

## 4. 一栋舍长与二花的合作约定

合作关系由下列内容组成，而不是一个笼统的“管理员”开关：

```text
人员：一栋舍长
智能体：二花
群聊：一栋相关群
责任人协作：舍长本人，以及明确指定的本栋负责人
日常私聊：尽量开放接待主动联系的人，在服务职责内持续交流
主动联系：按具体服务目的、合作约定、当前授权和对方意愿确定对象
职责：提供信息、持续训练本栋服务、修改本栋规则、审核、指定本栋事项确认人
限制：不得跨楼栋、跨智能体、跨未授权领域或改变社区共同原则
习惯：由舍长与二花启动时共同确认，例如汇报节点和提醒方式
```

厨房、收费、基金确认人、值日、普通问候等，都可以作为一栋职责范围内的具体主题；它们不自动扩大为全社区财务、全局任命或其他智能体的权限。

## 5. 二花接手后的最小工作闭环

```text
二花启动合作
  → 了解一栋当前重点、负责人和工作习惯
  → 收集居民信息与问题
  → 区分知识、动态事实和待处理事项
  → 按约定向舍长汇报或立即升级
  → 按知识可见性使用已确认的一栋知识，服务群聊和私聊咨询
  → 定期复盘过期、冲突和无人负责的内容
```

普通问候和正式入住欢迎分开：普通问候按一栋约定执行，不要求申请或 PMS 资料齐全；正式欢迎仍使用既定住宿、身份、成员、审核和发布条件。

## 6. 这张映射表先解决什么

- 让一栋需求包可以被完整承接，同时不把所有文件原样塞进二花 runtime。
- 让社区原则、一栋自治、动态事实和智能体工作方法各有位置。
- 让任何居民都能提供信息，又不会让未经确认的内容直接改变规则。
- 让一栋舍长通过合作启动和持续对话，逐步训练、纠正和完善二花。
- 让同一套框架以后服务二栋、三栋、小满、客房智能体和四老师。

框架职责和开放接待方向已确认，不再要求穷举生活事项清单。在住、过往、全部入住人员是具体通知或回访的对象筛选，不是日常私聊名单；受限知识另行核验访问资格。实际群绑定、人选和合作习惯在配置及启动合作时落实，本轮不导入真实配置。实现依据见[通用数据与入口衔接设计](../../../runtime/postgres/docs/data-design/2026-09-10-person-agent-collaboration-v1.md)。
