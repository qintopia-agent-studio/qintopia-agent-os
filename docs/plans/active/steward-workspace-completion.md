# 舍长工作空间与协作闭环完善

2026-09-23，负责人已授权开发、检查、提交和建立 PR。延续共同契约，不重新定义人员、任务或知识事实源。

## 已确认要求

- 管理员保留组织页面；舍长只操作本人本栋。主要内容使用顶部标签：对话、本栋知识、合作约定、事项与进展。任期和权限说明可按需查看。
- 历史使用可筛选、分页的列表与单条详情，不再堆叠无限折叠项。当前内容、修改人、时间、状态及前后内容可对照。
- 本栋知识支持 Markdown 文本导入、编辑、有效期和停止使用；正文是数据，不执行其中指令，不把普通知识冒充发布授权。
- 舍长在有效的指定业务确认人权限内，从系统核验的本栋当前在住名单选择临时审批代理，指定开始和截止时间，可撤销。退住、身份失效、授权撤销、到期均使后续审批失效。
- 临时业务代理不授予全局组织管理权，不靠改岗位名称获得权限。本切片执行用途为本栋欢迎内容审核；上层发布确认独立保留。
- 舍长可通过页面或二花设置本次／持续、先审／完整内容直接发及有效期。明确指令自身是确认，自主权限内不重复审批自己。
- 欢迎是合作约定内的具体事项，不是导航分类。待审正文、卡片、实际结果进入事项视图。既有成功、失败、未知结果与不重放语义保留。
- 页面与可信工具使用相同命令和持久记录。真实模型、渠道、上传与发送分别验收，不将固定对话演示称作微信闭环。

## 实施与验证

沿用 Person、范围授权、PMS 在住投影、Space 知识版本、WorkItem 与回执。扩展临时代理的执行判断和受控入口；旧迁移 checksum 不变。

保留其他对话未提交的五份规格，不纳入本次提交。前台生活经验与共建采集由其承接对话负责。基金、资源分配、完整值日不纳入本轮。上线前仍需真实身份、PMS 来源、Hermes
Runtime、Base 附件及渠道回执的试点证据。

### 候选查询：people / accounts / channels / groups

新增同源只读入口：

```http
GET /api/workspace/candidates?scope=<scope_ref>&kind=people&purpose=assign&search=<text>&limit=50&after=<cursor>
```

请求只接受表中字段；模型和客户端均不能指定 actor、tenant、网关凭据或改变权限。服务器从有效登录会话确定发起人，再按用途和当前 Policy 校验范围。

| 字段                           | v1 约定                                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `scope`                        | 已有范围引用； 必填， 不因为知道引用就允许查询                                                              |
| `kind`                         | `people`、 `accounts`、 `channels`、 `groups` 之一                                                          |
| `purpose`                      | `assign`、 `delegate_review`、 `contact`、 `set_groups` 之一； 按下表校验组合                               |
| `search`                       | 可选姓名、昵称、账号名称或群名称搜索，默认空；长度上限 80 字符；不支持按证件或完整手机号查询                |
| `limit`                        | 默认 50， 允许 1–50； 非法值拒绝， 不静默扩大读取                                                           |
| `after`                        | 可选 opaque cursor； 与 tenant、 scope、 kind、 purpose、 search 绑定； 不可跨查询复用                      |
| `subject_kind` / `subject_ref` | 只在 `kind=channels` 时成对必填；前者为 `person` 或 `work_account`，后者来自可访问候选，不接受裸外部账号 ID |

| 用途              | 可用种类                         | 权限与候选约束                                                                                                 |
| ----------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `assign`          | `people`                         | 检查当前组织任命管理权，仅查询其可任命范围；人员已可靠关联且有效。舍长角色复用现有同一角色定义，按任职绑定楼栋 |
| `delegate_review` | `people`                         | 检查本栋指定业务确认人的有效权限， 候选必须是本栋当前在住且身份可靠的人员； 不需要全局组织管理权               |
| `contact`         | `people`、`accounts`、`channels` | 检查该范围内已有工作连接和受众约定；个人与工作账号分开；账号来源可信且当前有效；查询不产生主动发送权限         |
| `set_groups`      | `groups`                         | 检查该范围当前群配置管理权； 候选必须来自已观测、 已登记、 可用于该范围的群目录， 不能任意输入外部群 ID        |

响应沿用 HTTP JSON 方式；成功为以下结构，失败为既有
`{ "code": "..." }`，不增加另一个错误封装。

```json
{
  "scope": "<scope_ref>",
  "kind": "people",
  "purpose": "assign",
  "configuration_version": 12,
  "items": [
    {
      "ref": "<person_ref>",
      "label": "张明（微信昵称：小明）",
      "description": "一栋 · 已关联人员"
    }
  ],
  "next_cursor": null
}
```

`ref` 为已有对应记录引用，客户端只保存/传递，不向使用者展示。

`configuration_version` 来自当前 tenant 配置版本，保存时沿用已有命令的
`expected_version`；不为 Person 或 Conversation 编造记录版本。

标签使用已有姓名与渠道昵称，缺少姓名时如实显示可用称呼、渠道和关系说明，不编造姓名。群或账号同名时加已有渠道/网关显示名称区分，不以昵称作唯一键。

- `people.ref` 引用已有 Person；响应不复制入住申请全文、证件、完整手机号或聊天内容。
- `accounts.ref` 引用已有工作账号；个人账号通过 Person 的 `channels`
  查询取得，不将共享小客服账号伪装为自然人。
- `channels.ref` 引用可信来源身份记录；额外返回
  `subject_kind`、`subject_ref`、`platform` 和
  `gateway_label`，供界面区分同一个人的不同账号。渠道稳定标识保留在服务端，不以返回的名称授权。
- `groups.ref` 引用已有 Conversation；额外返回 `platform` 和
  `gateway_label`；`SetGroups.conversations` 直接使用这些引用。
- 只返回该用途当前可选记录。未知、未确认、撤销、失效和跨范围对象不通过本接口冒充可选；身份管理中查看待关联记录仍使用既有专门入口。
- 每页重新检查登录、来源身份、范围、Policy、在住状态和受众约定；不依靠第一页的许可或已拿到的游标继续读取。排序按规范化展示名称和稳定引用确定，游标续页；不得截取固定前 256 项后在前端搜索。
- 列表不承诺事务快照。人员更名、任职或授权变化后可要求刷新；保存始终重新验证完整引用与当前权限。

### 候选查询的准确结果与在住条件

候选入口不把所有情况返回为空列表，固定返回以下状态。

权限判断先于候选查询与来源状态读取，未经授权不暴露来源和名单情况。

| HTTP | 响应                                         | UI 含义与动作                                                                       |
| ---- | -------------------------------------------- | ----------------------------------------------------------------------------------- |
| 200  | `items` 有记录，可能有 `next_cursor`         | 展示真实可选记录，可继续翻页                                                        |
| 200  | `items: []`、`next_cursor: null`             | 来源可用，但当前搜索没有符合本用途的记录；展示“没有找到符合条件的人员/账号/渠道/群” |
| 400  | `{ "code": "invalid_candidate_query" }`      | 字段、用途组合、游标或 limit 非法；修正请求，不降级成全目录查询                     |
| 401  | `{ "code": "authentication_required" }`      | 登录/身份已失效， 重新登录； 不显示旧候选                                           |
| 403  | `{ "code": "scope_access_denied" }`          | 当前没有本范围/本用途权限；说明无权，不提示“没有人员”                               |
| 503  | `{ "code": "candidate_source_unavailable" }` | 此查询需要的可信目录尚未接通或暂不可读取；说明来源不可用，保留筛选，允许稍后重试    |

“来源可用”指本次查询所需的受控目录和来源证据可以读取，不表示搜索时一定调用外部接口，也不表示已完成线上发送验收。

目录有效但没有匹配与没有可用来源分开判断；不以模拟条目填补生产目录。HTTP 错误正文不携带数据库错误、来源账号 ID 或凭据。

每页上限固定 50，默认 50。第 51 项仅用于服务器判断续页，不进入当前响应；合法 `after`
不能绕开该上限或当前权限。

当前在住仅在用途要求时检查：`delegate_review` 强制本栋当前在住；`assign`
不额外增加在住门槛，沿用该岗位既有任命规则。

`contact` 按现有 Audience 对当前、过往、全部居民及具体联系人分别判断；`set_groups`
只检查可信群、范围与管理权。

工作账号及其渠道按本范围已验证账号查询，不因居民住宿来源不可用而被屏蔽。动态居民来源的可用性仅约束需要解析居民名单的查询。

不得把临时欢迎审批代理的在住限制套用到全部工作人员任职、个人账号或联系目录。

### 任职与群绑定命令继续共用现有入口

`POST /api/preview` 与 `POST /api/save` 继续接收已有 `Command`：

```json
{
  "operation_id": "<operation_ref>",
  "expected_version": 12,
  "change": {
    "kind": "set_groups",
    "scope": "<scope_ref>",
    "conversations": ["<conversation_ref>"]
  }
}
```

`Assign` 与 `ConfigureWork` 继续使用已有 `Assignment` 及 `Audience`
类型，不新增按显示名任命命令。`Assign`
使用当前人员引用、共同舍长角色引用、已有职责引用、范围、智能体、任期及逐项权限；生产继续要求明确职责，不能使用 legacy
`actions`
代替权限配置。人员候选、任期、授予依据、确认主体和目标范围在 preview 与 save 中分别校验。

UI 从服务器当前状态取得 `expected_version`，一次逻辑操作固定
`operation_id`。preview 不写入，save 事务保存、返回既有持久回执。版本冲突保留用户草稿并要求回读；结果未知先查询同一操作的回执/当前状态，不换 operation
ID 自动重发。保存、替换、撤销或到期后的下一次 UI/工具请求读取当前 Policy 和知识版本，不需要改代码或重新部署。已开始的外部效果仍按既有不重放与未知结果规则处理，不能宣称已经撤回送达的消息。

### 正式知识与约定能力独立于网页聊天

`GET /api/state` 增加
`foundation_available`，只表示正式知识/约定服务入口已在当前服务模式启用；不表示当前操作者有修改权。

该字段由明确启用配置、实际 Store 模式和路由支持派生，与网页聊天、固定示例演示或二花模型是否在线无关。

```json
{
  "foundation_available": true,
  "dialogue_available": false,
  "dialogue_entry": {
    "mode": "existing_channel",
    "label": "通过已有微信或企业微信入口与二花交办",
    "reason_code": "web_dialogue_not_connected"
  }
}
```

生产 UI 可在 `foundation_available=true` 时调用既有正式接口，不得因
`dialogue_available=false` 隐藏本栋知识与约定维护：

| 入口                               | 请求及权限来源                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| `POST /api/foundation/rules`       | 已有 `ContextRequest`（`scope` 与可选 `topic`）；返回 `context`、`items`、`events`、`tasks`    |
| `POST /api/foundation/rule/change` | 已有 `RuleCommand`； `operation_id`、 `scope`、 `key`、 `kind`、 `expected_version`、 `change` |
| `context.permissions`              | 已有 `action` 与 `decision`；约定的 `change_rules`、知识的 `confirm_knowledge` 分别解释        |
| `decision.status`                  | 固定为 `autonomous`、`confirmation_required`、`denied`；UI 不按岗位名或聊天开关推断权限        |
| `decision.reviewer_name`           | 已有确认人显示名；没有确认人时为 null，不要求操作者辨认 Person ID                              |

`kind=rule` 消费 `change_rules`；`fact`、`culture`、`experience` 消费
`confirm_knowledge`。

新增/修改用 `change.action=save`，停止使用用 `stop`，撤销未来版本用 `cancel_scheduled`
并传已有 `revision_id`。

内容、起止日期、替换版本和恢复停止项继续沿用现有
`RuleEdit`。提交结果为实际保存或等待必要确认，不能把待审称作已经生效。

服务关闭时入口返回 `foundation_disabled`；当前操作者无本范围权限返回
`scope_access_denied`。

服务可用、当前无资料时仍返回本范围有效权限及空内容列表；这与服务关闭或没有修改权是不同状态。

每次读取、保存、停止和执行待审事项均检查当前身份与 Policy，旧页面上的按钮状态不能代替服务器判断。

### 对话可用字段与真实入口

在 `/api/state` 增加以下展示字段，不改变既有身份、工作关系和权限字段：

```json
{
  "dialogue_available": false,
  "dialogue_entry": {
    "mode": "existing_channel",
    "label": "通过已有微信或企业微信入口与二花交办",
    "reason_code": "web_dialogue_not_connected"
  }
}
```

- `dialogue_available`
  只表示当前 UI 的真实对话入口可用；不能由本地演示开关、岗位名称、能登录或数据库有记录推导为 true。本轮优先接通二花已有 QiWe 渠道工具；未接真实 Web 通道时该值保持 false。
- `dialogue_entry.mode` 只允许
  `existing_channel`、`demo`、`unavailable`。已有渠道说明可展示，但不把它包装成 Web 已接通；模式为
  `demo` 时明确“固定示例演示”，只能出现在隔离模拟环境。
- `reason_code` 使用
  `web_dialogue_not_connected`、`runtime_not_ready`、`identity_unconfirmed`、`scope_access_denied`
  或 null。界面把代码译成说明，不展示网关标识、token、Person ID 或内部连接地址。
- 二花在已有渠道中的真实工具以固定 profile、可信 session、经核验的 Gateway 和有效 Person/工作账号进入共同服务。

  人物、范围和当前消息来源不由模型填写；普通问题可按开放接待约定答复，但未关联账号不获得舍长维护权。

- 新生产入口必须明确生产模式、最小工具白名单和独立可信调用边界；模拟模式不能进入生产租户。进程凭据或发送者来源未被可信宿主约束时拒绝配置写入，不把同 UID 访问加 token 称作隔离完成。

### 认人与入住关联的业务结论

群聊/私聊发言先识别可信渠道账号，再通过有效来源身份关联取得同一个 Person。加入不同群不创建另一个人。

不同 Gateway、企业/应用及不同类型账号分别保存来源作用域，不能比较裸 ID 或按姓名/昵称自动合并。

QiWe 显示名缓存不是可靠 Person 关联；已有有效关联可复用，没有则保持未知。

申请与住宿采用负责人已确认的方式：系统以申请手机号、姓名、昵称及 PMS 每个实际入住人生成可解释候选。

疑点由岸岸在可配置运营工作群请有权小客服工作账号或主管确认，UI 共用事项。

不得把二花能主动私聊、住客已加好友或会回复当成流程前提。

候选分数不是“100% 身份证明”；只有可靠无冲突来源或具体有效确认才保存关联。

每次确认明确批准的是“申请 ↔ 实际入住人”还是还包括“具体渠道账号 ↔ 同一人”。

缺少渠道账号时可以先完成前一段，但不能宣称群聊/私聊已经认人。

确认后由共同服务保存来源、主体、时间、版本和关联，支持更正、撤销；默认不修改 PMS 住宿事实或飞书源字段。

逐个实际入住人关联，不将付款人/预订人当成全体入住人。

该业务规则沿用[社区模型现有决定](../../agent-os/community-business-model.md#2026-09-24-欢迎确认与内容归属补充)，

不把完整客房匹配/欢迎实施并入本轮舍长范围。
