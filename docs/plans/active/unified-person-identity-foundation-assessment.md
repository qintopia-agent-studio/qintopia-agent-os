以下是用户已确认的业务决定，不因旧实现不同而退回待决策：

1. 只有**填写了申请表且在 PMS 有可靠关联的住宿安排**，才进入欢迎制卡流程。两个来源可先后到达，任一来源变化都重新评估。仅有 PMS 的短住客不制卡；不新增住宿晚数门槛。
2. 统一人员库仍覆盖无申请的住客、员工、舍长、志愿者和外部联系人。
3. 申请与住宿关联满足后提前制作卡片、交小管家审核。预订已安排房态并占库存后，可按审核或有效持续授权发送预告；仅提交申请不预告。
4. 用户已明确取消固定等待一小时，改为**实际入住与对应目标群成员就绪后发送**：有效申请/逐人住宿关联、PMS 实际入住、当前目标群成员关系已确认、卡片与文案审核/有效授权均满足时，发送一次正式欢迎。规则中不再保留一小时计时或一小时自动放行。小客服服务的「秦托邦的小伙伴（新）」群也采用这一规则。预订阶段入群仍只适用预告，不能表述为已入住。任一条件变化都重新判断，已在群的住客无需退群重进。
5. 客房智能体协调；阿靓生成卡片；二花负责社区和楼栋群发布；四老师负责员工内部运营及内部群分发。小满负责社区营造、推动事件和活动，不是欢迎前置依赖。
6. 社区小客服确定大群文案，舍长确定本楼栋文案。内部在工作群由授权负责人批准，楼栋审核由二花私聊对应舍长完成，审批结果回写统一任务。
7. 首次明确授权、正常重复场景自动运行、变化或异常再找负责人。人员设置支持姓名、昵称和候选选择，不要求人查数字 ID。
8. 按用户决定，申请中的展示同意视为社区大群、对应楼栋群及员工内部群发布同意。仅覆盖相应展示内容，不等于允许披露申请中所有字段；撤回仍需使未发任务失效。
9. 欢迎卡片使用四老师已有脚本方法，目标迁给阿靓执行；附件写入住申请 Base。阿靓原设计产出 Base 与该 Base 分开，不混用。
10. 当前旧生产流程保持运行；影子测试和切换是未来实施安排，本轮不启用。

统一 `person_id` 就是现有
`persons.id`，不另发一套平行主键。生产 schema、已应用迁移、服务版本和现有调用路径需要通过只读 schema/版本检查确认，不能因开发者说「建好了」就认定所有关联与恢复服务也完成。

一个自然人可有多份 Application、多次 Stay、多个渠道账号、多个同时或先后生效的工作角色。工作岗位是 RoleAssignment；共享「小客服」账号是渠道工作账号，其实际批准操作者需要单独留证，不能永远绑定为某一个自然人。

同名、手机号更换、共用手机号均只生成匹配候选；名字搜索命中不等于身份确认。稳定、可信且无冲突的外部引用可复用已有确认，首次跨系统绑定无可靠证据时请小客服确认。一个家庭/多人订单应逐入住人关联，不将订单会员资料复制给所有 occupants。无申请的老客仍建身份/住宿关联，但是否复用旧申请进入本次欢迎须有明确规则。

人员合并、误绑定撤销建议采用追加事件与可撤销链接：保留旧 Person/渠道/申请/任务引用，记录旧、新归属、原因、确认人和版本，派生画像/卡片/未发任务重新评估。已有事实 revoked_at 不是完整“撤销人员合并”实现的证明。

## 4. PMS：实体关联、事件与同步工作量

### 4.1 已有的实际关联能力

- `member_external_references`
  已保存 member、property、provider=FEISHU_BASE、来源容器/表/记录引用，member
  detail 查询会按成员和物业取回。申请关联不是从零开始；尚未确认生产历史填充率。
- `orders.member_id` 可空；`order_occupants`
  有独立 ID、order_id、PRIMARY/ADDITIONAL 与身份快照，**没有直接 member_id 列**。会员/付款方不必是实际入住人。
- `stays`、`stay_segments` 表达住宿及安排历史；`inventory_units`
  有 ROOM/BED、parent_room_id、building_code。楼栋来自当前有效住宿安排关联的库存单元，不按申请意向房型或旧卡片猜测。
- 订单详情返回 occupants、occupantCorrections、stay、currentSegment、effectiveArrangement、fulfillment、amendments 等。申请与订单会员的引用可以缩小候选，但仍需识别真正入住的那个人。
- Stay 状态契约包含 PLANNED、IN_HOUSE、COMPLETED、CANCELLED、NO_SHOW、CHECK_IN_REVOKED。查询中出现历史记录不等于现在应欢迎；维修、内部占用也不能仅因有库存占用就进入欢迎。
- 认证为 Bearer，具备过期/撤销、物业范围、READ/WRITE 上限，并结合主体授权收窄。首期集成只需只读住宿接口，不需要把 WRITE 权限交给模型。

**负责人现在不需要提供手机号、证件、真实住客样例或自己查 ID。**技术侧用接口契约和合成案例完成结构验证：会员甲代实际入住人乙预订、多人订单、无会员订单、同名申请、撤销入住人等。未来实际匹配出现歧义时，由小客服在受控界面/任务中选对实际入住人；全自动匹配前再以授权的只读聚合检查证明填充率和一致性。

### 4.2 已有状态不等于已有事件接口

本次对 Green PMS 的 `apps/`、`packages/`
中 TypeScript/SQL 检索 webhook、outbox、事件订阅/流及 updatedSince/updatedAfter 等入口，未发现对应实现；这是源码检索范围内的结论，不排除仓库外服务，但目前不能依赖它。

| 所需能力                          | 当前证据                                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 新建订单/入住/换房/退房/撤销      | 有命令、状态、amendment/版本契约；无对应已验证外部事件投递                                                   |
| 事件签名、订阅版本、稳定 event_id | 未发现现成对外契约                                                                                           |
| 发生时间、实体版本                | 有 amendment created_at、sequence、prior/new_version 等可复用基础；业务生效时间和入库时间需区别              |
| 可靠发送、失败重试、重放          | 有业务事务/command receipts；未发现 webhook 投递队列/重放服务                                                |
| 增量同步                          | 订单有 updated_at/version，但 OrdersQuerySchema 无更新时间过滤；beforeId 按 created_at/id 翻页，不是变化游标 |

PMS 命令在同一事务中应用业务效果、更新房态修订、保存回执和审计，是未来增加事务 Outbox 的可复用边界。需覆盖所有会影响住宿事实的已提交写入路径，包括后台纠正；不能只在 HTTP 返回后发一条请求，也不能把 preview 或未提交命令当事件。

### 4.3 两种入口共用一个 Inbox

**Webhook 与 Inbox 不是替代方案。**Webhook 和轮询是发现变化的方式；Inbox 是两者都需要的持久接收、去重和恢复基础。

```text
PMS 业务事务 + Outbox → 投递 Worker ─┐
PMS 变化查询/轮询 + 定期状态对账 ────┼→ Agent OS Inbox → 同一规范化/状态处理器
Feishu 最小记录事件 ────────────────┘                    → 客房流程 WorkItem
```

建议事件带来源实例/物业、event_id、schema_version、实体 ID/版本、amendment 引用、发生/生效时间；

不带整份住客资料。

固定服务端订阅接收方，签名/时间窗口/重放校验后持久接收，成功落库再 ACK。

PMS 投递独立于业务事务，失败进入重试/死信，不拖垮 PMS 业务提交。

Inbox 分两层去重：投递用来源 event_id；业务变化用
`source + property + entity + revision + fact_type`。轮询若只有快照，先存 observed_version/hash，再由同一处理器生成状态变化，不按每次轮询时间创造新的欢迎资格。旧版本不能覆盖新状态；同版本冲突先回读权威系统。可靠游标须处理同时间多记录、分页期间更新、事务提交乱序、撤销/删除及游标过期；只按最大时间戳推进不能保证无遗漏。

正式欢迎的幂等按“逐人住宿流程 + 阶段 + 逻辑目标群 + 内容类型”，不把 Artifact 改版当作新发送资格。来源、目标路由和批准版本作为执行证据保存。重放和实时路径不各写一套业务逻辑。

### 5.2 更正前次判断

“没有跟二花说过话就没有 QiWe 身份”不成立。**渠道用户 ID 的存在不依赖发言**，可以通过群成员名单或联系人列表先发现。本仓库已有
`--sync-room-members`、按目标群解析成员和标记过时成员的代码，优先复用，而不是重造身份扫描器。

但需要区分三个完成度：

1. 发现渠道账号：名单/事件提供 QiWe userId。
2. 确认群成员关系：目标群、类型、当前有效状态及观察时间。
3. 认识实际的人：渠道身份与 Application/PMS/Person 可靠关联，且二花可读该范围的安全背景。

前两步不自动证明第三步。即使添加的是企业微信“小客服”，官方标识是否对当前应用可见仍受账号类型、企业/应用权限限制；如果是普通微信服务账号，也不能据“加了小客服”就断言已取得官方 external_userid。

入群回调 → 在 3 秒内完成验证及最小 Inbox 持久接收/ACK

定期成员/联系人对账弥补回调遗漏。只接收允许账号和允许群的事件；不能为测试直接替换 QiWe 全账号共用回调地址。现有同步代码不是实时事件已经接线或生产运行的证据，本轮未调用真实 QiWe 接口、抓取成员名单或改变回调。

| 身份类型                       | 建模方式                                                                                           |
| ------------------------------ | -------------------------------------------------------------------------------------------------- |
| 企微外部联系人 external_userid | platform=wecom、企业/实际应用作用域、id_type=external_userid；以真实接口作用域为准                 |

### 6.4 影子方案与切换

用户提出新旧并行验证是合理方向，但要区分“接收观察”与“两个流程同时生产执行”：

1. 后续开发完成后，新增最小标识事件旁路到新接收器，旧流程仍是唯一生产执行者；当前本轮不改 Workflow。
2. 影子消费者使用独立执行模式/作用域，持久记录最小接收和模拟状态，只产出脱敏拟执行计划；**不生成真实卡片、不写 Base/PMS、不发送消息**。发送/上传能力在执行层关闭，不能只靠 prompt。
3. 飞书旁路只传受控资源引用、事件类型/时间/版本等必要元数据；读取申请仍需限定字段。若 Workflow 无可靠修改版本，通知只是“需回读”的信号，接收器回读当前状态并比较 hash。
4. 观察新增、后补申请、预订、入住、换楼栋、取消等状态是否得到预期计划；附件写回字段与系统自写变更必须从业务触发中隔离。
5. 切换前以固定起点/版本和执行权开关围住唯一发送者，先停旧副作用再启新；影子积压不自动转真实发送，历史申请不自动重放。
6. 回滚先停新发送/上传，再恢复旧流程；依据逐任务回执处理切换期间已执行动作，不能简单回放全部积压。

不需要把所有 Base 自动化全改成 Hermes
webhook。保留本地公式/视图等有用自动化，将需要跨系统持久协作的触发统一接入 Agent
OS。字段/权限变更导致失败时保留任务并告警，恢复权限后对账，不丢弃失败事件。物理拆表可后做；最主要迁移成本在引用、字段映射、权限和 Workflow，建立适配层可降低后续业务代码修改。

| 小满         | 社区营造、活动及事件推动；独立 Event/WorkItem 接入，故障不阻断欢迎                                   |
| Agent OS     | 人员、角色与授权、事件、工作项、调度、审核证据、发送门禁、审计及恢复                                 |

社区小客服的大群文案确认通过内部工作群的可追溯任务完成；客房负责协调，四老师可承担内部交互入口。楼栋若设置先审，由二花私聊舍长传递本次卡片和文案，不要求客房再重复问一次；本栋明确设置完整欢迎做好直接发时，在持续授权范围内不逐次请审。每个目标独立判断审批或适用持续授权及共同资格，一栋待审不阻塞另一已就绪目标；共用同一卡片也不共用目标授权。

**MCP 是受控能力调用协议/入口；

Tools 是有结构化输入输出的具体业务动作；

Event/WorkItem 是持久事实和协作状态。

**它们不能互相替代。

MCP 返回成功不等于消息已经送达；

自由文本“帮我通知某群”不具备正式任务、权限或回执语义。

旧 Agent 直调只可作为受控入口，转换为同一 WorkItem 并执行同样门禁，不能保留旁路直发。

固定不变量：身份/住宿事实源、字段公开范围、人员/群权限隔离、发送时点下限、已撤销审批不能执行、幂等与审计，均不可被普通训练对话绕过。负责人可在任职范围内调整语气、模板、可用公开变量、预告/欢迎偏好，并按共同契约设置本栋完整欢迎直接发或先审。

持续授权默认至撤销或任职结束，不强加频繁续期；绑定任职、逻辑群、动作、模板/可变字段范围及版本。负责人换人、目标楼栋改变、披露范围扩大或模板越界时重新核验相关授权，历史记录保留。只免文案不自动免卡片；明确完整欢迎免审则覆盖约定卡片和文案，不再额外等人工。两种模式均不能取消实际入住、目标群成员和个人信息许可条件。

设置先做最小 Web 表单/列表便于查看和交接，四老师提供同一服务的对话入口；按姓名/昵称搜候选、用楼栋/角色区分、授权任命人确认，后台持久化稳定 ID。同名不能自动选，群管理员事件也不能自动任命舍长。

## 9. 脱敏场景走读与剩余业务决策

本轮完成下列**纸面场景评估**，没有执行测试代码或真实业务操作。

| 场景                            | 应有结果/待定边界                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------ |
| 先申请，后 PMS 安排             | 前者只建案例，二者可靠关联后才制卡；占库存且获批后预告                               |
| 先安排，后补申请                | 申请到达后重新判断；已入住则不补发“将来到访”的过时预告                               |
| 有 PMS 无申请                   | 可建立 Person/Stay，不生成欢迎卡片或欢迎发送                                         |
| 同名/共享电话/会员代订/多人订单 | 待确认逐人关系，不能自动串人；仅符合资格的 actual occupant 进入流程                  |
| 多申请/老客再来                 | 同一 Person 可保留多申请；选哪份、旧表是否本次有效仍待业务确认，建议小客服一次性选择 |
| 预订后取消/退房/撤销入住        | 停止不再适用的未发任务；历史记录不自动补发                                           |
| 等待发布期间换楼栋              | 发送前重读当前安排，撤销旧目标待发任务；新目标重新校验成员与本群授权，社区已发不重复 |
| 审核撤回/任职变更/展示同意撤回  | 相关未发任务暂停；已发内容是否更正/撤回由负责人决定                                  |
| 实际入住但目标群成员未知/未入群 | 不按时间自动放行；复用成员同步补证，仍未知则延后或请负责人确认；没有固定一小时等待   |
| 影子积压/服务重启/乱序回放      | 调度时点落库，恢复后重验当前资格；不追发不适用历史任务                               |
| 图片成功文字失败/一个群失败     | 按目标和内容分别恢复；成功部分不重发，未知回执先查询或人工核对                       |
| 新卡片版本/附件回写             | 绑定新审核版本，但不新增同阶段已完成发送资格；不触发循环制卡                         |

需要负责人后续确认的决定，仅剩业务选择：

- 旧申请复用与多申请选择；建议本次案例显式关联所选申请，不自动拿所有历史资料混合生成。
- 入群未知/未入群的超时升级、人工确认入口与任务最晚有效窗口；固定一小时已取消，不能因等待够久而自动认定已入群。成员已入群也不证明已看到消息。
- 已发预告后取消/改楼栋，何时需要更正；撤销入住后重新入住是否视作新的欢迎阶段。
- 谁可任命社区/楼栋/内部负责人，接任时如何接续持续授权；姓名/昵称交互已定，不再要求手工填写 ID。
- 固定 PMS
  webhook + 补偿查询方向已获用户确认；具体开发切片/估算按共同契约及 PMS 技术核对收敛，首个欢迎流程不开放 PMS 写权限。
- 公共文案变量/照片的具体白名单与各类资料保留期；内部群适用展示同意已经确认，无需重复问。

### 13.2 接收器是什么

接收器就是 **Agent
OS 的服务端接口**。按来源使用各自认证/解析适配器，验证来源、限制资源范围、做最小字段投影并将事件写入统一 Inbox，成功持久接收后 ACK。它不要求 Hermes 模型在线，也不在接收 HTTP 请求的过程中等待制卡/审核或群发送；不同来源不能共用一套未经区分的凭证/签名规则。

客房 Agent 是该责任域中的业务协作者；WorkItem/规则服务保存与推进流程状态。旧飞书 HTTP
POST 改接新入口、最小标识协议和影子旁路均属将来上线步骤，目前继续保持旧流程。

### 13.3 “没说过话也能认识”的合成业务场景

以下“小林”是合成人物，不是真实住客资料：

1. 小林填申请、加社区企微小客服。Agent
   OS 从申请建立 Application，经已有引用或小客服首次确认，把该申请、PMS 实际入住人和小林的官方外部联系人身份关联到同一 Person；没有可靠证据则先待确认，不能按同名自动关联。
2. PMS 已安排住宿，资格满足后制卡审核。此时小林不必向二花发任何消息，档案已经可以存在；二花能否读取仍由授权范围决定。
3. 负责人把小林加入指定楼栋群。QiWe 产生群成员变化事件，接收器落 Inbox 后异步取当前群名单，找到新成员的 QiWe
   userId；不能把回调外层操作者 senderId 当新增成员。
4. 若当前账号可调用 /contact/openid，将 QiWe
   userId 转为官方 external_userid，命中步骤 1 已确认的同作用域渠道身份，于是知道“这位群成员就是这个 Person”。保存转换来源与群成员关系。
5. 二花此后拿到的只是该群/业务可见的称呼和安全背景，不是完整申请。即使小林从未在群里发言，也可被识别；若转换失败、应用作用域不一致或没有先前已确认链接，就进入待匹配，不装作已经认出。
6. 入群信号遗漏时由名单对账发现。同一个人在多个群出现，复用 Person，分别保存每个群的当前成员关系。

这会明显降低渠道身份关联成本，但只是补上“QiWe 账号 ↔ 官方渠道账号”的一段桥梁，不能凭 external_userid 自动推导“飞书哪份申请/PMS 哪位入住人”。本轮只核查了供应商文档与代码，未实测生产账号转换/群事件权限；不能把以上目标路径说成已经上线。

### 13.4 新欢迎触发：条件汇合，不再固定等一小时

用户再次明确确认取消一小时等待，不保留固定延时或按一小时兜底发送；此前确认的实际入住与审核条件继续有效。小客服服务的「秦托邦的小伙伴（新）」群与对应楼栋群均按下述规则，各群独立判断成员就绪、授权与是否已发送。

「秦托邦的小伙伴（新）」是用户指定的业务群名称；正式接入时通过受控群配置绑定实际渠道群，并核对与历史社区大群称呼的对应关系，避免重复配置同一群。本轮只记录业务范围，不查询或保存真实群 ID，不改变生产发送目标。

对每个社区/楼栋目标分别判断：

```text
有效申请与实际入住人/本次住宿已可靠关联
  AND PMS 当前已实际入住
  AND 住客当前在该目标群内（新入群事件或有效名单证据）
  AND 对应该目标的卡片/文案审核或有效持续授权就绪
  AND 披露同意/负责人权限/当前楼栋路由仍有效
  AND 本次住宿的该阶段/目标尚未发送
→ 创建或唤醒唯一发布 WorkItem；二花执行前复核，然后发送
```

满足最后一个条件时推进，因此不能只监听“入群”单一瞬间：

| 顺序/例外                         | 结果                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------ |
| 已入住、已审核，再入群            | 入群核实后可发送，不等一小时                                                   |
| 预订后先入群，尚未实际入住        | 只允许预告；PMS 后续实际入住时重新判断并发送正式欢迎                           |
| 已入住/已在群，卡片稍后审核完成   | 审核事件使条件汇合后发送                                                       |
| 老客本来就在群                    | 读当前有效成员关系，无需等待不存在的新入群事件；旧申请是否适用另按本次关联决定 |
| 只进社区大群，没进楼栋群          | 大群满足条件可先发；楼栋群等待，各自幂等                                       |
| 同一次住宿退群后重新加入/回调重复 | 不重复欢迎；未发送前若退群则暂停该群任务                                       |
| 同一人再次住宿                    | 使用本次 Stay/流程实例；历史已发不能错误压掉本次合法欢迎                       |
| 换楼栋/取消/撤销入住              | 重新取权威状态与目标，撤销不适用待发任务                                       |
| 入群未知或转换失败                | 同步/人工确认后再推进，不能一小时到了就当作已入群                              |

社区与楼栋群适用该成员条件；员工内部群不应要求住客加入。内部任务仍由四老师按工作人员审批及住宿阶段处理；取消等待后内部发布的具体时点可在内部模板策略中明确，不能偷偷沿用住客群成员门禁。

这样取消的是人为缓冲时间，不是实际入住、身份核实、审批或重复发送控制。正常业务减少等待；复杂性集中在共用状态与任务基础中，使用者只处理真实例外。
