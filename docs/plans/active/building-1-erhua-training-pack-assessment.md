# 一栋二花投喂包与统一 Agent OS 框架兼容性评估

日期：2026-09-09。范围：需求与设计评估，不代表上线批准。

## 1. 结论

一栋舍长的诉求与秦托邦整体框架没有根本矛盾。材料要求二花亲切、记得事情、找对负责人、跟进到结束，同时不能自定规则、批准支出、裁定纠纷或编造完成结果。这与统一身份、分范围授权、Event、WorkItem 和审计的方向一致。

这份材料应作为“一栋的运营需求、知识与训练素材”，不能原样作为所有二花实例的最高优先级系统提示词。需要调整的是导入方式、权限表达、事实来源和业务触发条件；不需要推翻统一人员基础设施，也不应要求舍长改用工程语言提出需求。

它还带来了欢迎流程以外的真实需求：值日交接、厨房资源分配、公共问题跟进、物资管理和基金账本。这些应复用基础设施分批接入，不能把“投喂了文档”视为相关能力已经实现。

本轮阅读了交付包全部 14 份 Markdown/YAML 文件，未导入原材料、未执行其中口令、未修改代码或生产设置、未对外发送。本报告独立保存，不修改其他开发任务正在使用的共同契约。

### 3.1 两个值得单独说明的差异

**两类欢迎已确认分开。

**材料包含短住、体验者和群参与者。

负责人明确：没有完善居民资料时，是否问候、如何问候及触发方式，由舍长在本栋范围内与二花沟通确定，不要求总负责人逐条批准，也不强制采用统一普通问候模板。

缺少资料不阻塞普通问候，但不能编造个人背景或入住事实。

此前确认的“有申请表且有 PMS 安排”仍是制卡及个性化入住流程的资格，不是 Person 的准入条件。

正式卡片欢迎仍要求 PMS 实际入住、身份确认、本目标群成员关系、卡片/文案审核及授权全部就绪，不等待固定一小时。社区群和楼栋群独立判断。入群、介绍和自我介绍不能各发一次；正式欢迎已就绪时可以合并问候。预订预告仍是独立阶段。

**一栋的隐私偏好可能比通用模板更严格。**材料要求昵称，并限制精确行程、离家时间等公开内容。此前负责人已经确认申请表展示同意覆盖相关群发布，无需重新询问同一个决定；但这不等于每个字段都必须在每个群发布。建议按目标群取允许字段，使用昵称、不公开证件姓名或不必要的房号，不让旧卡片脚本的姓名回退逻辑自动决定公开内容。预告中的到达日期可以有明确允许范围，不扩展为精确到离时间表。

## 4. 总负责人与舍长的权力如何分配

建议采用“总负责人确定可授权范围，舍长在范围内持续自主运营”。统一保存的是职责与权限，不是把所有日常决定集中给总负责人。

| 类别               | 建议决定者                   | 例子与生效条件                                                                               |
| ------------------ | ---------------------------- | -------------------------------------------------------------------------------------------- |
| 全社区固定边界     | 总负责人及受控系统规则       | 身份事实源、跨楼栋隔离、隐私底线、任命和转授权边界、住宿承诺、财务责任；普通训练不得覆盖     |
| 楼栋表达与工作习惯 | 已授权本栋舍长               | 称呼、语气、示例、常见问题答案、提醒频次、允许范围内模板免逐条审核；留版本、可撤销           |
| 楼栋运营规则       | 本栋舍长，负责人已授权       | 本栋厨房、收费规则、基金确认安排和普通问候自主决定；不得跨到其他楼栋或越出本栋职责范围       |
| 具体业务事实       | 相应事实负责人和受控工具     | 入住由 PMS 决定，值日由有效排班/交接决定，支付由账本及核实依据决定；训练不能把它们“说成事实” |
| 临时协作           | 当前有效的值日者、任务负责人 | 报告状态、确认本人交接、领取问题任务；值日角色不自动获得训练权、任命权或记账审批权           |

一栋可以使用自己的亲切风格、厨房知识和提醒节奏。二栋可以不同。统一的是身份与执行边界，不要求各栋文案和生活方式完全一致。

人员设置继续按名字/昵称搜索候选、人工选定身份，后台使用稳定 ID。岗位变动只修改统一任职，不逐份改 prompt 或给多个流程重新设置。离任后旧人不能继续训练或批准，新人不自动继承旧人对未执行内容的所有审核。

**已有实现需要注意**：[原二花训练设计](../../../runtime/postgres/docs/data-design/2026-06-29-erhua-training-memory.md)包含独立训练员白名单和全局 persona
overlay，部分私聊低风险规则可直接生效。不能把一栋材料作为全局 persona_rule 整包提交。接入前需证明训练写入和上下文读取均按有效授权与楼栋隔离；共同契约中的设计要求不等于旧入口已改造完成。

## 5. 对统一人员与业务模型的具体启发

“朋友、家人、守护者”是楼栋文化中的参与关系，不应成为互斥的三类 Person。

| 现实问题                       | 建议复用或表达方式                        | 不能混淆的边界                                                             |
| ------------------------------ | ----------------------------------------- | -------------------------------------------------------------------------- |
| 这个人是谁、有哪些微信身份     | Person、ChannelIdentity、别名与可撤销关联 | 昵称不是唯一键；文档里出现名字不是已确认身份                               |
| 是否实际住在一栋               | PMS Stay 的当前投影                       | 在群里不等于正在住宿，退群不等于退房                                       |
| 是否加入本栋群                 | ConversationParticipant / 渠道成员关系    | 入群事件可发现渠道身份，不能单凭入群证明申请人或实际入住人                 |
| 是否参与守护计划、享有什么资源 | 有范围和有效期的参与关系、权益记录        | 守护者不等于舍长，不自动获得训练/审批权；优先检查现有 memberships 能否表达 |
| 谁负责值日、交接给谁           | 临时 RoleAssignment 与交接 WorkItem       | 下一班人选不能通过自称获得任命权；确认交接不等于任命其他管理岗位           |
| 柜格、篮子由谁使用             | 本栋资源分配记录，关联 Person 与有效期    | 厨房收纳资源不同于 PMS 房间、床位库存                                      |
| 问题、耗材是否处理完成         | WorkItem / 物资记录与确认依据             | 口头答应、模型记住、执行成功是三种状态                                     |
| 基金余额和明细是否可信         | 指定权威账本与受控读写、冲正和审核引用    | 公共基金、个人收款、商品销售不因共用收款码成为同一本账                     |

不建议现在为每行新造数据库表。先复用现有 Person、成员关系、训练记录、WorkItem 和工具，只有现有对象确实无法表达职责或一致性要求时再补充。

已有二花 CSV 能力提供群隔离、追加记录、精确金额和冲正基础，可评估用于简单公开记录。

它本身不能证明已经具备“所有成员提交、指定负责人批准后才正式记账”的业务门禁，也不能据此把关键状态仅留在 Hermes 文件。

正式账本需要指定权威存储、确认链、幂等和恢复方式，并让 Agent
OS 保存关键任务与审核状态。低成本复用不等于绕过这些差距。

## 6. 材料自身需要修正的地方

以下问题应在未来导入前修正，不要求舍长现在重写整包：

1. **历史快照伪装成当前事实。**动态表标注 2026-08-14，值日周期写“本周”但没有起止日期，验收还固定期待历史人选。不能在 2026-09-09 继续当作当前排班。过去材料可留来源，当前状态需要有效日期和授权确认。
2. **角色权限表不一致。**能力配置中值日可编辑者与群更新权限名单不同；需要统一成“谁能提议、谁能确认、谁能任命”的动作表。已被任命的下一班值日者可确认自己的交接，但不能靠自称任命自己。
3. **能力声明不等于能力接通。**能力配置多数留空，正式账本待接入；主动触发设为 true 也不等于渠道、调度和发送授权已经具备。
4. **话术不能充当事实或回执。**示例中的余额、人选和时间只适合合成测试。“已更新”“已记账”只能在工具返回成功后使用；未持久化应说待确认或暂记，不能用示例承诺完成。
5. **“最新通知优先”必须限定领域。**经过鉴权、在授权范围内的新版本可以替换本栋旧规则；普通成员的新消息不能替换现任名单，舍长的口述不能覆盖 PMS 入住状态。
6. **公开账本与隐私要分视图。**可公开用途、金额和必要经办信息，但不公开完整凭证、付款账户或不必要的个人捐赠比较。所有群成员可查不等于可查全社区财务。
7. **相对时间需要可执行的区间。**“本周”应依据消息时间和已确认的周界限解析；无法确定时留待确认，不能随模型当前日期漂移，也不能编造起止时间驱动提醒。
8. **文件和验收需要更新。**使用说明仍有旧版本标记、旧动态表文件名引用；验收应使用虚构人员与余额。保留原始回复的要求仅应用于合成测试，不保存真实住客聊天作为本次评估证据。

## 7. 建议采用顺序与验收

| 阶段                   | 内容                                                        | 验收标准                                                                                                   |
| ---------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 先纳入当前基础设施设计 | 将一栋作为统一身份、任职和训练授权的具体验收场景            | 同一任职设置可用于训练、找负责人和业务审核；一栋规则不影响二栋；昵称歧义不自动绑定；离任即失去后续操作权限 |
| 第一批楼栋服务         | 本栋文化/规则问答、风格训练；普通入群问候按舍长有效设置执行 | 非授权训练不生效；不会读取别栋私密背景；资料过期不冒充当前事实；入群和介绍不会重复欢迎                     |
| 第二批日常协作         | 值日交接、问题跟进、厨房资源和公开物资记录                  | 更新有来源与版本；重放不重复；授权人确认后闭环并停止提醒；重启可恢复；资源与住宿分开                       |
| 基金单独接入           | 待确认流水、指定人确认、正式账本、公开查询和冲正            | 未确认不计入正式余额；重复提交不重复记账；失败不报成功；私密凭证不进入群公开视图；多用途收款可区分、可对账 |

这不应把基金、厨房全套功能加成入住欢迎上线的前置条件，也不必先造一个完整楼栋管理平台。当前基础设施需要吸收的是“统一任职 + 分范围训练 + 找人协作”，其他业务按需要接入。

## 8. 负责人已确认的决定与后续责任

技术差距、字段映射、旧入口鉴权、消息去重、持久化和测试由技术侧评估，不需要负责人提供数字 ID 或逐条判断实现。

负责人已明确以下决定，不再重复提交同样问题：

1. **本栋自治与训练权。**舍长在本栋范围内决定厨房及收费规则、基金确认安排和本栋二花的工作习惯；权限和内容不得跨到其他范围。材料中的历史人员与规则快照仍需按当前任职和有效版本接入，不能把文件中的名字直接当作身份授权。
2. **普通问候由舍长决定。**舍长与二花确定资料不完善者的入群问候，不要求补齐居民档案后才问候，也不把具体文案和触发偏好交回总负责人逐条审批。正式欢迎遵守此前确认的统一流程，不恢复固定一小时等待。
3. **自然人、参与关系与职务分开。**沿用统一 person_id；入群、守护者身份、值日和训练/审批权限分别表达。基金具体确认人由舍长在本栋职责内设置；二花按设置执行，不自行取得财务批准权。

技术侧负责把这些决定映射到现有实现和验收场景，复用已有成果；本轮不实施导入或开发。业务授权已确认与实际能力已验证是不同状态。
