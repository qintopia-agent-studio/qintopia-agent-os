## 新决定的衔接与待明确项

“本体基础与欢迎闭环”任务回报以下最新用户决定，已要求其写入专项报告并附可定位来源：岸岸直接在“全村人运营团队”呈现卡片和文案、发起客房确认，不经四老师转发；可在 UI 配置有权确认者与目标群，群与 UI 使用同一事项；客服和主管应能在有效权限内补位。

协调解释如下；若原用户决定另有含义，凭来源回总指挥核对，不由任一线自行扩大：

- 欢迎卡片/文案及资格确认与 PMS 订房、收款、入住确认分别绑定各自的操作效果和权限。前者的确认不能代替后者。
- 阿靓负责制卡；二花依本栋规则承担后续审核传递或欢迎发布。岸岸向运营团队呈现内容，不自动改变最终欢迎发布者。
- 四老师仍辅助主管管理规则、例外和协调，无需成为每次客房确认的转发环节。
- 目标群必须绑定可靠渠道标识；成员在群中或拥有主管/客服名称不自动取得业务执行权。补位依据当前职责、物业/楼栋范围及精确操作授权。
- 用户已明确“秦托邦小客服”可在本轮欢迎确认中作为指定可信工作账号主体，不追溯每班自然人。不按昵称认人或自动赋权，账号主体须诚实标注；共同身份契约由基础线实现，不伪造自然人 Person。此决定不扩大 PMS、资金或其他业务权限；每笔收款仍需要对具体订单、流水和金额明确确认。
- 照片和欢迎卡片统一，楼栋欢迎词优先采用本栋舍长措辞；统一资料/卡片与楼栋措辞分别保存版本。仅措辞调整不重做客房事实确认仍为实施建议，不豁免楼栋审批；事实或披露内容变化须按影响复核。
- 面向使用者显示姓名、渠道昵称等可理解的信息，避免用内部 Person
  ID 要求人辨识。中文测试描述统一使用“模拟”。

### 申请与身份关联补充决定

保留飞书申请；系统用手机号、姓名、昵称与 PMS 逐个实际入住人生成候选，已有可靠链接可复用。不确定时由岸岸在“全村人运营团队”集中请可配置的“秦托邦小客服”工作账号或有权主管确认，UI 使用同一事项。必须明确渠道账号、人员/申请、每个实际入住人之间哪段关联获确认；缺账号或证据保持待关联，模糊分数或单一候选不自动认人。

确认后由共同服务保存 Agent
OS 来源关联、确认主体和版本，不修改 PMS 住宿事实或飞书源字段。身份关联确认与卡片内容确认分别记录效果，可以同一事项呈现，不混用批准。

不默认二花可以主动私聊住客；自助私聊仅在渠道可达时作为可选补充。

共同主体、授权、关联服务及欢迎入口仍由基础线维护；岸岸只提供住宿、申请、WorkItem 引用及接线。工作账号的欢迎关联权限不扩大 PMS 权限，每笔收款仍须有权人确认具体流水、金额和订单。

3. 岸岸先收口可独立验收的 PMS 能力与最小共享扩展，基础线提交身份/欢迎接口的清晰增量。公共身份或宿主协议若确有依赖，先提交接口提供方，再由调用方整合；不预先按任务名称强制合并先后。
4. 合并前比对双方公共文件、schema 与迁移，运行受影响的共同身份、授权、欢迎及 PMS 回归。分别通过不代表整合版本通过；无需无理由反复跑所有无关测试。
