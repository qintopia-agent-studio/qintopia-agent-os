# 本体、业务记忆与受控工具：秦托邦 Agent OS 如何认识人和理解业务

日期：2026-09-22。

用途：记录本次对话中从“要不要建立本体”到“怎样以最少开发工作落地”的理解过程，供以后复习。文中的人员与厨房规则都是虚构例子。

这是学习记录，不是上线证明。具体开发标准见[社区业务模型](../../agent-os/community-business-model.md)及[人员与智能体实施方案](../../plans/active/person-agent-foundation-execution-plan.md)；后续实现状态以对应代码与验收记录为准。

## 一、为什么会讨论本体

最初的需求是：智能体要懂我们的业务，认识社区里的人，知道当前是谁在说话，以及对方要做什么。

定时任务可以让程序在指定时间运行，但它本身不定义人员、职责、业务关系和权限。让二花或四老师理解社区，需要明确这些内容如何表达、从哪里取得，以及什么时候有效。

例如，同一个人可以同时是住客、一栋舍长和某次活动的组织者。离任后，他可能仍然是住客。把这个人简单标记成“舍长”，无法完整表达这些关系和变化。

本次判断：秦托邦需要明确、共享的轻量业务模型，现有人员与协作基础已经在承载这项工作。当前没有必要为了“做本体”先引入 OWL、RDF 或新的图数据库。

## 二、本体到底是一个什么东西

本体是一套对业务概念、关系及成立条件的共同定义。它没有唯一的文件形式。

| 形式              | 表达或保存什么               | 例子                                   |
| ----------------- | ---------------------------- | -------------------------------------- |
| Markdown 业务文档 | 概念、边界、规则及解释       | 任职有范围和任期；入群不等于入住       |
| 数据库结构与记录  | 对象、具体关系、来源和历史   | 甲当前担任一栋舍长                     |
| 服务和工具代码    | 查询关系，校验规则，处理变化 | 查当前负责人；离任后拒绝旧权限         |
| 智能体上下文      | 本次任务需要且允许使用的信息 | 当前说话人的身份、职责、适用规则与待办 |

所以，MD 可以描述本体，数据库可以保存具体实例，服务可以把定义用于实际工作。数据库模型可以实现本体定义的一部分，但“建了表”不能直接等同于“建立了本体”。上表列的是业务模型的定义、存储和使用环节，不是说每个环节单独就是本体。

例如，数据库外键能保证“任职关联到一个存在的人”，但“舍长只能在获授权的本栋范围内修改规则”还需要业务定义和程序共同落实。我们目前采用的是具有本体思想的轻量业务模型，未建立完整的形式化本体。

例如：

- **概念定义**：一个人可以有多项任职，每项任职有范围和有效期。
- **具体事实**：甲现在担任一栋舍长。
- **具体授权**：甲的这项职责允许他修改一栋厨房规则。
- **当前意图**：甲这次是在询问关闭时间，还是要求修改关闭时间？

前三项为理解提供依据，最后一项仍需结合这次对话判断。本体不能仅凭“他是舍长”就推断他每句话都是正式指令。

知识图谱通常把具体对象及关系组织成图，本体为它们提供共同含义。复杂关系也可以通过关系数据库查询，并不必然需要图数据库或正式逻辑推理引擎。

## 三、业务文档只给人看吗？它是不是智能体的记忆

讨论中纠正了一个不完整的说法：业务文档不只是供人审阅，业务定义也应成为智能体理解和执行任务的依据。

但每次执行需要的是当前任务适用的上下文，不要求把所有 MD 和人员资料重新读一遍。

| 内容           | 例子                       | 作用               |
| -------------- | -------------------------- | ------------------ |
| 业务概念与规则 | 舍长的职责有范围和任期     | 理解社区如何运作   |
| 当前业务事实   | 甲目前是一栋舍长           | 知道现在是什么情况 |
| 个人背景与偏好 | 甲偏好简短沟通             | 知道如何合作       |
| 工作记忆       | 昨天约定的活动还缺场地确认 | 持续推进事情       |

这些内容可以共同构成智能体使用的业务记忆。本体主要定义它们的结构和含义，记忆保存具体内容及变化，上下文则是这次实际交给模型使用的部分。

“系统保存了”不等于“模型这次看到了”。需要由程序提供或由智能体调用工具取得，而且要按身份、用途和范围裁剪。

这里的记忆是系统保存、检索并提供给模型的信息，不是大模型通过训练把这些事实学进了自身参数。UI 更换舍长后，数据库更新了事实；系统把新事实放入后续任务的上下文，模型才能据此处理。这不会自动改变模型本身。

聊天记录里的旧记忆也不能决定当前权限。昨天是舍长，今天已经离任，执行时就不能继续按昨天的权限办事。

## 四、UI、数据库和智能体怎样连起来

人的直观入口是 UI。我们通过界面维护人员、岗位、职责、任职关系、工作范围和权限，后端校验后把结果保存到数据库。

```text
人在 UI 修改职责或任职
        ↓
后端检查并保存到数据库
        ↓
智能体通过业务工具取得本次需要的上下文
        ↓
理解请求，提出或推进动作
        ↓
后端在真正执行前重新检查当前权限和相关状态
```

智能体不需要像人一样打开网页操作，也不会因为 UI 保存成功就自动知道变化。程序必须接好查询和执行入口。

这里要区分两种修改：

- “把一栋舍长从甲换成乙”是任职变化。
- “舍长负责哪些事情”是职责定义变化。

修改职责模板是否影响已有任职，需要明确规则。现有方案中，修改模板不会自动增加所有在任人员的权限。

## 五、SQL 是什么，受控工具又是什么

SQL 是查询和修改数据库的一种语言。可以把数据库理解成很多张彼此关联的表，SQL 能表达：

> 找出目前一栋的舍长。
>
> 结束甲的任职，登记乙的新任职。

让智能体自由执行 SQL，就是让它自行编写数据库指令。它实际能读写哪些内容仍取决于数据库账号权限；如果权限过大，可能查到不该看的资料或误改记录。

受控工具则是预先做好明确的办事入口：

| 工具含义     | 智能体提出的请求       | 后端负责的事情                           |
| ------------ | ---------------------- | ---------------------------------------- |
| 查当前负责人 | 谁负责一栋这项工作？   | 查有效任职，判断范围，返回允许展示的结果 |
| 查本人职责   | 当前说话人能负责什么？ | 根据可信渠道身份识别人，查询有效职责     |
| 检查动作权限 | 能否修改这条规则？     | 判断自主、需指定人确认或没有权限         |

这类似办事窗口：智能体提出明确请求，程序负责查档案、核验条件和提供结果。后端内部仍然可以使用 SQL。

本次已确认的标准：智能体通过受控服务或工具访问业务数据，不开放自由 SQL 或通用数据库凭证；UI 与智能体使用同一套有效身份和授权服务。

工具名称本身不会带来安全性。真实发起人应来自可信渠道或登录信息，不能让模型填写一个名字或人员编号，就冒充那个人。

## 六、每次查数据库会不会慢？能否变更后通知更新记忆

讨论中提出的方案是：第一次读取后保存起来，UI 变更时发事件通知，更新智能体记忆。

这个方向在工程上通常叫“缓存加事件更新”。缓存是一份为加快读取而保留的副本；事件通知告诉相关组件某些数据已经变化。

它可以减少重复查询，但也增加了需要处理的问题：

- 通知可能延迟或暂时未送达。
- 智能体或服务可能离线，恢复后要补齐变化。
- 多个会话可能各自保留不同版本。
- 旧任务可能已经受理，但在真正执行前发生离任或撤权。
- 即使没有人修改 UI，任期也可能自然到期，或者预先保存的新规则到达生效时间；旧缓存因此不再适用。

因此，即使以后引入缓存，也应由系统管理版本、变更失效和时间到期，不能只依靠 UI 修改通知或聊天记录自行记住变化；关键动作执行前仍须检查有效状态。

本次没有实测这条查询链路的耗时。范围明确、索引合适的数据库查询通常比一次模型生成快，但具体体验仍要测量，也要考虑网络和工具调用次数。

## 七、为什么 MVP 最后选择直接查询

负责人明确了当前优先级：先追求最高效的实现，体验优化不是首要任务。

因此最终采用：**通过受控服务按需直接查询现有数据库，关键动作执行前重新校验。**

具体做法：

1. 每个需要业务背景的对话轮次，一次集中取得必要的身份、任职、范围、规则和相关事项；同轮可复用。
2. UI 保存成功后，后续查询结合生效时间、结束时间、撤销状态和适用范围，读取当前有效的事实；已保存不等于已生效。
3. 修改规则、审核、发布及排队任务真正执行前，后端重新检查当前身份、任职、授权和相关版本。
4. 数据库内的校验与写入遵循事务和并发约束，避免检查完以后状态变化，却仍按旧结果写入；外部动作还需要独立的执行记录和回执。
5. 暂不新增跨轮业务上下文缓存或“通知智能体更新记忆”的链路。已有业务事件、审计和任务恢复机制继续使用。
6. 实测出现性能瓶颈后，再考虑查询优化或必要的缓存。

例如，今天保存“下周一由乙接任”，不代表乙今天已经具有该任职权限。查询应按任期和当前时间判断，不能简单地把最后保存的记录当作当前事实。

数据库事务也不能保证外部动作一起成功。群消息已经发出后，数据库回滚不会自动撤回消息。发送仍需独立记录执行过程、处理回执并防止重复执行；结果不明时先核对，不能直接当作失败重发。

选择直接查询，是因为当前开发环节更少，也少了一套缓存失效、通知投递和恢复机制。这是针对现有基础和 MVP 目标的工程选择，不是经过实测证明的性能最优方案。这里的“直接查询”是后端服务查询数据库，仍遵守受控工具标准。

## 八、用“更换舍长”复习整条链路

以立即生效的换任为例，你在 UI 把一栋舍长从甲换成乙：

1. 后端结束甲的任职，登记乙的新任职及相应授权，保留历史。
2. 下一次甲或乙找二花时，系统根据已确认的渠道身份识别人，查询当前任职。
3. 二花取得的本轮上下文体现人员变化，无需相信旧聊天中保存的“甲是舍长”。
4. 如果甲之前发起的规则修改还在排队，实际执行时重新校验，失效权限不能继续使用。
5. 甲若另有独立且仍有效的任职，应按那项任职自己的范围和权限处理。

三个重要验收场景因此是：同名不误认、跨栋不越权、离任后失效。还要有正常授权请求成功的场景，不能把一律拒绝当作系统正确。

## 九、这次讨论时已有基础与尚待完成的事情

依据本次对话核对的本地源码，已有人员与渠道身份、安全成员上下文、任职授权配置、任务和审计等基础，也已有专门的成员查询与二花回答上下文工具。

但协作工作台里的新任职、职责和授权，还没有完整进入二花实际对话与执行链路。业务模型里有表、工具里有查询、界面里能保存，都不能单独证明整条链路已接通。

本次把受控工具标准及 MVP 选择写入了开发文档，未因此完成运行代码接线或生产验收。这一状态是讨论时的记录，之后应查阅最新实现与验证结果。
