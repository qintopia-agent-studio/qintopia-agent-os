## 2. 统一能力管理建议

| 名称                 | 职责与落点                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| Agent Profile / SOUL | 岸岸身份、工作边界、模型及工具装载选择；仓库契约在 `agents/anan/`，运行态按既有 Profile 分发边界管理 |
| Skill 说明           | 给模型的工作方法和业务步骤；不能授予权限或代替程序校验                                               |
| Tool                 | 模型可调用的具体操作；受控参数、当前授权、持久执行和真实结果由代码落实                               |
| Hermes Plugin        | 把工具和能力装载到 Hermes 的集成包或注册层；不是另一个业务事实库                                     |
| MCP                  | 对外暴露工具或资源的标准协议；按调用和进程边界选用，不要求每项能力都另起 MCP Server                  |
| 能力包               | 统一持有实现、文档、manifest、测试和依赖；可同时包含 Skill 说明、Plugin 注册和 Tool 实现             |

`skills/` 在本仓库是工程能力包目录，不等于里面只能放一个 `SKILL.md`。既有
`skills/qintopia-tools`
已规定主要保留注册与兼容入口，不能把新 PMS 实现继续堆到通用注册文件。

建议采用开发计划已允许的 `skills/pms-operations/` 作为 PMS 能力包，`agents/anan/`
选择并注册该能力。首期仅岸岸获准使用；代码可复用不等于所有 Agent 都取得操作权限。共同身份、授权和持久事项继续由现有共享服务负责；PMS 仍拥有库存、计价、资金和住宿事实。

通过现有
`registry/skills.yaml`、包 manifest、Agent 工具声明及适用的动态权限共同管理。包声明表达依赖和可装载范围，程序仍须核验当次人员授权；不新增通用插件商店或平行权限库。

发布时保证插件及其依赖来自相容的受审版本，运行态凭据、会话和个人记忆留在既有安全位置。

首期使用受控 HTTP 客户端接 PMS 原生 API 即可。若将来需要 MCP 接口，应复用同一实现和鉴权，不能重新实现另一条可绕开确认的写入通道。

## 3. 需要落实的接线边界

1. 官方 WeCom 宿主提供可信请求人、消息与会话，再映射共同 Person 和范围；当前 QiWe 模拟来源不能当作此接线已完成。工具参数不能自填操作者或批准人。
2. 当次有效能力取人员授权、岸岸工具范围及 PMS 主体/Token/物业权限的交集。PMS `/me`
   返回的是执行主体权限，不证明发言人具有该权限；查询也须控制范围和披露。
3. 有权客服对相同具体方案的明确决定可以复用，PMS 技术 Preview/Confirm 不增加两次人工确认。参数、预览或权限失效按原契约重验；各业务动作独立保存结果，UNKNOWN 先核对原键。
4. 查询可直接返回。等待确认、写入、恢复和跨 Agent 交接必须经过共享持久服务；插件内不能只用内存或聊天历史保存这些状态。业务请求不需要新增独立网络中转服务，但不能绕过共同授权与执行记录。
5. PMS Token 的安全绑定和工具宿主权限须匹配。Profile `.env`
   和同 UID 不构成强隔离；若运行时可任意执行代码并读取该凭据，工具校验不能被宣称为不可绕过。真实启用前确定已有隔离执行边界或必要的最小执行组件，本地先用模拟凭据验证。
6. 收款与申请复用同一办理链。申请统一入口及四老师原职责仍需阶段 4 核实；支付 feed 不是已上线推送。后续欢迎继续由岸岸协调、阿靓制卡、二花审核传递或发送。
7. 保留用户已有岸岸 SOUL、模型与渠道设置，后续按实际版本对齐 Profile 清单、装载、服务和回滚。不能从仓库旧模板覆盖用户配置，也不在本轮修改发布或 CI 流程。
