# 秦托邦协作框架：当前实现的逻辑复核

本次按用户要求重新分析，不修改界面、业务代码、数据库或运行配置。依据是本任务此前已确认的沟通、当前源码及既有验证记录；一栋投喂包仅是需求适配案例。

**结论：当前交付是带本地持久保存的开发原型，尚未完成已讨论的框架 MVP。**

本地保存、撤权和部分范围检查已经实现，但用户应能完成的组织配置、职责维护和关系调整还不完整。此前使用“闭环已完成”“已修正”的表述，容易让人认为框架已达到可用程度，需要纠正。技术测试通过不能证明产品逻辑符合用户的工作方式。

## 已明确的命名与理解

- 最上层是“秦托邦”。测试环境应通过页面角标表达，不应把组织名称写成“合成社区”。
- 对象名称统一为“智能体”。“合作”描述连接关系，无需把对象命名为“合作智能体”。
- 用户指出岗位不能增加、删除或编辑，结合前文，理解为当前维护能力不足；不是禁止未来维护岗位。
- 人、智能体、职责、工作范围都需要能够被选择、查看和连接。岗位用于组织任职与常用职责，仍需灵活维护。

## 当前到底能做什么

| 使用者想做的事                           | 当前实际状态                                                            | 判断                         |
| ---------------------------------------- | ----------------------------------------------------------------------- | ---------------------------- |
| 选择人员                                 | 可选本地虚构人员，复用现有 Person；本页不能接入新人员或管理真实任职人员 | 原型能力                     |
| 选择智能体                               | 读取随程序编译的仓库登记清单；不代表正在运行或可用                      | 有清单，未完成运行状态接入   |
| 新建合作记录                             | 可以选择一个人、岗位、智能体和范围，预览后存入本地库                    | 已实现部分基础能力           |
| 新增岗位                                 | 页面有新增表单，服务端有新增命令                                        | 有入口，但只有名称和权限类别 |
| 编辑“小管家”等现有岗位                   | 卡片没有编辑按钮，服务端没有编辑命令                                    | 未实现                       |
| 给现有岗位增减职责、移除岗位             | 不能调整岗位定义，也没有停用或删除入口                                  | 未实现                       |
| 单独维护“职责”                           | 没有独立的业务职责目录；只有固定权限项和文字说明                        | 核心概念缺失                 |
| 调整一条关系中的人员、岗位、智能体或范围 | 编辑时这些字段被锁定；只允许改说明和权限，换人要手工结束旧任职再创建    | 不符合灵活连接的完整要求     |
| 维护范围                                 | 可新增范围、调整群绑定；没有范围重命名、停用等完整操作                  | 部分实现                     |
| 让真实智能体按设置工作                   | 真实登录、合作引导、知识确认、训练与发送入口尚未接入                    | 未实现                       |

所以，“新增岗位表单存在”不能回应“现有岗位不能维护”的问题；“已经能保存”也不能回应“框架是否能用”。

## 第一处根本错误：把职责等同于权限

“负责什么”和“能决定什么”应分别回答。

| 概念     | 人能理解的例子                                         | 应怎样维护                                               |
| -------- | ------------------------------------------------------ | -------------------------------------------------------- |
| 岗位     | 舍长、小管家、技术负责人                               | 可新增、编辑、安排任职、停用；不是写死的人员类型         |
| 职责     | 楼栋居民服务、客房协调、活动运营、智能体技术支持       | 可命名、描述和复用，连接到相应的人、智能体和范围         |
| 授权边界 | 能确认本职责的知识；能调整服务方式；哪些内容需要谁审核 | 在具体连接中明确，不因填写一段职责描述自动放权           |
| 合作习惯 | 如何汇报、何时提醒、哪些工作先做                       | 智能体启动合作时引导责任人确认，不由本次设置者替他们决定 |

当前代码把“确认知识”“审核”“发布”“技术支持”等放在同一组固定权限中。这既混合了业务职责与执行动作，也要求用户先理解权限系统，再想办法表达工作安排。上一轮只把这些选项解释得更长，仍然没有修正这个概念错误。

建议让人先选择职责，例如“楼栋居民服务”，再在这条关系里明确知识确认、指导方式和内容审核的边界。职责可以复用，不为厨房、书架或每一次通知分别创建系统权限；底层少量受控动作仍然保留。

## 第二处根本错误：图上有连线，却没有保留每条连接的完整含义

现图按智能体聚合：左边是一组人，中间是二花，右边是一组范围。一栋和二栋舍长同时连接二花时，两人的范围关联只能靠小字补充辨认。职责也只是人卡片上的权限标签，没有成为可查看的工作关系。

这容易让人读成“这些人都通过二花负责这些范围”。源码中的授权检查仍按单条关系的范围隔离；本次没有发现这一画法导致后台自动授予跨栋权限。问题在于界面不能准确表达实际连接，不能靠后台安全来弥补人的理解困难。

每条连接都应能还原为一句完整的话：

> 某人以某岗位，与某智能体，在某工作范围内承担某职责，并按约定的权限边界工作。

以下是结构示例，不是已配置的真实任命：

| 秦托邦中的人员 | 岗位       | 职责           | 智能体                   | 工作范围                   |
| -------------- | ---------- | -------------- | ------------------------ | -------------------------- |
| 人员甲         | 舍长       | 楼栋居民服务   | 二花                     | 一栋：所选群聊及适用私聊   |
| 人员乙         | 舍长       | 楼栋居民服务   | 二花                     | 二栋：所选群聊及适用私聊   |
| 人员丙         | 小管家     | 客房协调       | 已登记并可用的相应智能体 | 已选择的客房工作范围       |
| 人员丁         | 技术负责人 | 智能体技术支持 | 所负责的智能体           | 指定的支持事项和相关责任人 |

两行中的二花是同一个智能体；两位舍长的工作边界仍分别绑定在各自关系中。公司负责人、社区负责人、各栋与横向技术支持都放在秦托邦框架内，不因图的位置自动产生授权继承。

## 第三处根本错误：预置岗位成了不可维护的清单

当前初始化中，除技术负责人外，各岗位都获得同一组“技术支持以外的可选权限”。这些选项本身并未自动授予真人，但也没有表达小管家、舍长和社区负责人的职责差异。上一轮只移除了舍长的技术支持选项，仍没有完成通用岗位与职责维护。

建议在岗位详情中能直接改名称、说明及关联职责，并看到涉及哪些人员和工作关系。用户移除岗位时：未使用的草稿可删除；已有任职或历史的岗位停用并保留历史。不能让一个删除按钮悄悄连带结束某人的全部工作。

岗位方案的调整也不能悄悄扩大所有在任者的权限。应列出受影响关系，让有权者明确选择如何更新；新增职责方案与授权生效分开记录。这是实现建议，尚未作为新的业务决定写回共同契约。

## 第四处根本错误：修改对象和修改连接没有形成自然操作

使用者的常见动作是“给这个人安排职责”“给二花指定某范围的负责人”“把这条工作关系交接给新人”。当前主要入口仍是一张必须依次填写的长表，其他页面多是只读目录。关系编辑又锁定了人、智能体、岗位、范围和任期，迫使用户理解底层记录才能调整组织。

更自然的 MVP 建议如下：

| 从哪里进入   | 使用者能做什么                                                       |
| ------------ | -------------------------------------------------------------------- |
| 秦托邦总览   | 查看范围归属和工作连接；按人、智能体、职责或范围筛选                 |
| 人员详情     | 查看岗位与职责；增加、调整或交接他承担的工作                         |
| 智能体详情   | 查看各范围由谁负责、谁能指导、遇事找谁                               |
| 岗位与职责   | 分清岗位定义与职责定义，分别新增、编辑、停用，并查看关联影响         |
| 范围详情     | 查看绑定群聊、私聊约定以及该范围有哪些人员和智能体负责               |
| 任一连接详情 | 同时看清人、岗位、职责、智能体、范围、权限和任期；准确调整这一条连接 |

这些入口使用同一份关系数据，不各自建立权限系统。MVP 可先用可点击的关系图、清晰的关联列表和侧边编辑面板，无需先建设自由拖拽画布。

“结束与二花的某项合作”和“结束这个人的小管家任职”应为不同动作。现实现有任职结束与单项撤权，却没有完整的单条合作结束和交接入口，不能将前者当作后者替代。

## 第五处缺口：工作范围尚未覆盖已确认的群聊与私聊逻辑

现在能维护的是楼栋／业务范围与群的绑定；私聊接待、主动联系、信息可见性只写成了说明。这符合当前没有真实执行接入的状态，但还不能算相应配置能力完成。

后续仍沿用已确认决定：开放接待主动来聊的人；主动联系按事情、职责、约定与意愿判断；在住、过往、全部入住人员是具体任务的对象筛选，不成为每条关系的封闭私聊名单。智能体与负责人确认工作节点和习惯；“能聊”“能修改知识”“能主动发送”分别判断。

技术支持也应表达“为哪些责任人提供哪类支持”。当前只有人到智能体的授权记录，尚未明确支持对象关系。

## 为什么会偏离，以及哪些已有代码可以保留

问题来自实现顺序：先做授权表与保存接口，再把这些字段直接变成页面；遇到产品反馈后，局部增加标签、说明和连线，没有重新检查四类对象及其连接是否成立。

可以保留 Person 的稳定身份、本地数据隔离、事务保存、重复提交处理、审计、范围验证和撤权机制。需要重整的是业务职责的表达、岗位和范围维护、连接的生命周期，以及所有页面读取同一条完整关系的方式。不是单纯换标题或调整颜色，也没有依据要求丢掉所有已验证的基础代码。

## 重新判断框架 MVP 是否完成的标准

1. “秦托邦”是唯一最上层名称；页面清楚区分业务对象与测试状态。
2. 能维护岗位、职责和范围；小管家、技术负责人等预置项与新增项使用同样的维护方式。
3. 可以从人、智能体、职责或范围进入，建立和修改同一条明确的工作连接，不靠姓名或图形位置判断权限。
4. 同一个二花与一栋、二栋的人配合时，图与列表都准确显示各自职责和边界。
5. 可以只结束或调整一条合作，不误结束该人的其他职责；换人、代理、停用保留历史和可读的影响说明。
6. 已保存的配置和已接入的执行能力分别显示；智能体未接入时不表现成已开始工作。
7. 完整框架后续还须验证新责任人合作引导、知识确认和实际入口约束，不能把本地配置原型称为这些能力已完成。

这些是对已确认需求的复核与具体实现建议。本轮先交付分析，不继续追加界面补丁，也不重新询问已决定的人岗规则。
