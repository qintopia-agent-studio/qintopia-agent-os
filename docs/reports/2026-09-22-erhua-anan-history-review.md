### 岸岸与普通员工同等权限的评估建议

负责人询问：是否可以把 PMS 给员工的权限都给岸岸，以保留灵活性、主动性并保障安全。本节给出建议，未执行赋权，也不把该询问解释成开放全部自主写入。

- `apps/api/src/auth.ts`、`packages/db/src/command-authorization.ts`：API 按当前主体、物业、命令授权、Token 上限及功能开关判断；令牌绑定的执行主体不会自动变成群里发指令的人。
- `apps/api/src/server.ts`：Web 与 Agent 复用 Preview/Confirm 入口；预览归属特定主体，不能假设客服能直接确认另一个 Agent 主体的预览。

因此，应纠正此前将退款登记、改价等笼统列作“扩大的操作”的表述。普通员工本来可以做的受控业务，不因为经由岸岸就统一上交主管。

`RECORD_REFUND`
登记已发生的退款事实，不向支付平台实际划款；同等 PMS 权限不授予另一个系统的支付执行权。

建议岸岸的可办理能力以当前普通员工业务权限为基线，不合并所有员工与管理员的权限；具体技术授权仍用 PMS 的精确命令及物业范围，未来新增能力不能靠一句“全部权限”跳过接入和验证。

分别保留两种执行依据：

1. **代员工办理**：岸岸能调用的能力、本次员工的有效业务权限及其明确指令共同约束动作。岸岸更宽的服务权限不能成为低权限人员的越权通道；员工与 PMS 主体的可信映射和逐次校验需要接通。
2. **按持续授权主动办理**：由有权主管明确事项、条件和范围，岸岸在其中自行执行并留证；未获持续授权的经营判断仍由有权人员作出。查房、准备方案和发现问题的主动性不需要依赖无限写权限。

同一有效业务确认不重复询问。客服临场选择可以偏离推荐，但不能绕过 PMS 库存、资金和状态约束；“同等权限”也不自动改变原先已明确需要客服确认的预订、收款和实际到店事实。

这与先前“执行有依据、权限可审计”的原则一致，也扩展了早期只接少量工具的设想。PMS 现有机制提供基础，Agent
OS 仍缺群内真实操作者、PMS 权限与批准依据的联动，不能宣称发出一枚 Token 就已完成。

UI、通过四老师通报主管或直接联系主管。

建议知识中明确区分：PMS 必须遵守的条件、主管明确的经营约束、可以临场调整的经验建议。不能把主管讨论中的所有倾向都写成强制拦截条件，也不能把所有业务约束都降成建议。

每条经验可表达适用情形、推荐做法、理由、例外和来源版本，由四老师结合现有交流提炼，系统维护元数据。可提供可读的 skill/Markdown 说明，但执行仍取同一知识源的有效版本，提示词或知识内容本身不授予权限。

例如岸岸建议连续安排同一房间，客服根据当次客人偏好选择其他可售方案；条件和权限均允许时办理，不因违背推荐增加主管审批。这只改变当次处置，四老师可收集反馈提出长期改进，不自动改写全社区策略。

UI 接手应保留事项和操作关联：岸岸停止继续提交同一动作，先核实在途或未知结果；客服用自己的权限处理，岸岸依据 PMS 结果更新进度和后续建议。当前还需实现交接与对账，不能承诺无缝接管，也不能用客服换账号另建动作来重试未知结果。
