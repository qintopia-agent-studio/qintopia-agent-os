# 欢迎事项身份关联与运营确认：本地实现及交接

## 结论与范围

本轮新增欢迎事项内的独立人员/工作账号确认主体、配置、原子关联与内容确认、群/UI共用记录及发布前复验。当前是本地受控入口，不是线上身份匹配与欢迎送达的完整交付。

依据：[直接用户决定与只读审计](2026-09-24-welcome-identity-and-review-audit.md)。用户决定的默认路径是“系统找候选 → 岸岸在运营群找有权客服或主管确认 → 自动保存关联”，不依赖主动私聊未加好友的住客。确认者和运营群可配置；秦托邦小客服是工作账号，不伪造自然人。照片/卡片统一，本栋欢迎词与发布规则仍由舍长决定。

本轮读取项目入口、路线图、变更路由、工程护栏、协作/测试/迁移规则、Postgres、Sidecar及共同身份/欢迎包规则。实施使用既有工作树
`.worktrees/pr720-ci-reconcile`、分支 `codex/welcome-identity-audit`，以岸岸阶段1/2
`201b961129e301af10af360ad9a94859674ea32a`
为依赖；未修改根工作区。CI/基础设施调整规则不变，本轮不修改 CI 或部署归属。

## 实现与接口

- 新迁移 `202609240003_welcome_subject_confirmation.sql`
  和对应数据设计：工作账号、确认配置/授权、事项、版本化收据；不改旧迁移或 checksum。
- 旧 `Actor`、`verify`、`gateway_actor` 与 PMS `read_business`/`execute_business`
  保持原语义。工作账号仅获明确授予的欢迎事项身份/内容确认权。
- 服务端内部入口：`Store::welcome_review_open_task(None, &ReviewOpen)`；DTO 在
  `person_collaboration::welcome_model`，字段为
  `work_item`、`scope`、`case_ref`、`application`、`artifacts`。前四项为 UUID，最后为产物 UUID 列表。必须已有
  `anan → anan` 的 `welcome_event` WorkItem，其 payload 的
  `tenant_key/case_ref/scope_ref/application_ref`
  与请求精确对应；不能拿收款事项或模型自报引用替代。
- HTTP 操作仍要求真实本地登录会话和 CSRF；`None`
  不是 HTTP/模型可提交的参数。运营配置需原体系的身份/审核管理授权，确认授权有截止时间，换配置撤销旧授权。
- 三种效果分别勾选：申请与实际入住人、渠道账号与人员、本版内容及许可。同一次提交可原子办理关联和内容；缺少条件或版本冲突整体回滚。
- 同一事项支持部分确认、退回、撤销和重新整理；幂等收据保留原确认者、效果、授权和版本。只撤销本事项建立的关联，不改 PMS 原始住宿事实或飞书表单。
- 既有欢迎发布决策新增运营确认复验，之后仍经过本栋原门禁。运营状态与舍长手工暂停独立，确认/撤销不会解除或改写舍长暂停。
- 岸岸工作入口内使用“事项与进展 / 协作安排”标签、候选姓名/昵称、卡片与文案预览、说明图标。组织岗位中已有岸岸客房协作时提供同一入口。内部 ID 不作为选人标签。
- Broker 仅放行 `anan` 的
  `welcome_operations_list/decide`；校验可信群消息、配置群、账号和范围。确认须有宿主认证消息中的精确
  `welcome_confirmation`，模型解释普通“同意”不能授权。

## 尚未完成与下一步

1. 真实飞书/PMS手机号、姓名、昵称和入住时间的候选投影与匹配未接入。当前候选来自已有来源人员/申请人员，不是模糊匹配引擎；仅有相似度、唯一候选或手机号相同不能自动认定身份。候选不足保持待关联。
2. 企微宿主交互按钮/消息到 `welcome_confirmation`
   的可信映射、岸岸真实群呈现尚未接通。本地 broker 测试不证明真实运营群已经可以确认。
3. 二花全部旧入口尚未支持复用工作账号确认建立的人员关联。旧个人解析未放宽；新增欢迎主体路径可识别这种关联，不能宣称跨所有入口已认人。需补真实群聊、私聊、跨平台转换、改昵称与撤销后的联合验收。
4. 列表目前最多100条事项、最多100个渠道候选，尚无历史分页；不能声称所有历史可读。新用户没有已有人员候选时仍须由受信来源建立人员，不通过欢迎接口随意新建 Person。
5. 真实照片/卡片、内容许可、入群事件、目标栋、舍长审核或直发、发送回执/UNKNOWN恢复与正式制卡能力迁移须继续联调。岸岸阶段3事件接收及迁移002由另一任务交付，本线003不接管该实现。
6. 不含真实群发、生产写入、合并主线或部署。人工验收需在完整整合版本上进行，代码提交和本地测试不代表线上可用。

## 验收顺序

先确认模拟账号的范围及协作安排，再验证少量候选、部分关联、一次确认、内容改版、配置更换、撤权/到期、退回撤销和舍长暂停。随后按001→002→003在全新隔离库验证整合迁移；线上试点前补齐真实资料投影和企微确认入口。住客未加二花好友不得阻断运营群办理。
