## 自动关联结论及最小后续路线

本次证明了稳定渠道账号有可用接口基础，但没有证明“进群账号 → 申请 →
PMS 逐个实际入住人”的可靠完整关联。不能报一个未经计算的成功率，也不能用候选相似度代替可靠身份。

建议后续依次验证，具体新接口、来源写入和生产配置按各自授权实施：

1. 查明当前 QiWe 转换入口的受支持接法；优先现有能力，不为一次测试改基础设施。核对企业/应用作用域，使用真实返回的账号映射复测一栋、二栋。
2. 核查已有 `follow_user.state`
   的来源和语义，检查原申请入口是否曾保留可信渠道引用。现有样本仅证明 state 存在，不证明它包含申请关系；没有依据时不猜测。
3. 若历史证据确实不足，在正常申请或接待数字入口自动携带经过验证的渠道账号，并关联申请及 PMS 逐人入住引用。可评估同一开放平台下的微信登录与 unionid 对接；属于待验证方案，不承诺现有飞书表单天然提供此能力。仅发送专属链接不能证明填表人就是目标账号，仍须可信登录/回调上下文。
4. PMS 输出住宿事实与来源引用，Agent
   OS 维护共同身份、任职、任务和确认记录；不要求工作人员再建一份人员台账。同行人、代付、换号、多人共用账号及歧义分别保留状态，不能为提高覆盖率误合并。
5. 入群事件触发欢迎处理，尚未建立可靠关联时停在“暂未对应入住资料”，不得展示别人的卡片或自动发送。实际入住、内容许可等既有条件仍须满足，除非用户明确改变该业务规则。

### 飞书与 QiWe 手机号实际比对

通过 lark-base 读取当前申请表单配置：“姓名”“手机号码”已经必填，手机号仍是文本字段，必填不等于验证码验证。分享读取返回 anyone、require_login=false；不把飞书登录标识当作微信身份。

查询范围为申请表全表，省略 View 和筛选，仅投影手机号；440 行且 has_more=false。

Python 仅为候选比对去除空白、括号、短横线和 +86/0086 前缀，接受严格 11 位大陆手机号，不纠正错字、不改源值。

431 行符合该格式，403 个不同手机号，24 个手机号对应多条申请；重复可能来自再次入住或重复提交，不能直接视为多人共号。

QiWe 读取一栋、二栋全部群成员及对应联系人详情，以联系人响应的 userId 对应请求，不依赖名字。手机号用单次随机密钥 HMAC 后做相等比对，原始申请投影放在受限临时目录并自动清除，手机号、账号明细和临时 HMAC 不作为证据保留。

| ---- | ------------------------- | ---------------------- | ------------ | ------------ | -------------------- |
| 一栋 | 35 / 35                   | 4                      | 2            | 0            | 2                    |
| 二栋 | 16 / 16                   | 5                      | 2            | 0            | 3                    |

### 群聊与私聊识别人：已有基础与实际边界

同一账号换昵称不应变成新人。不同微信/企微账号及不同渠道标识，仍需要可信来源映射或有效确认，不能因姓名相同自动合并。“收到消息后知道是谁”与“二花能主动私聊他”是不同能力；未加好友或渠道不可达不能作为必须私聊核验的前提。身份可跨会话识别，不代表私聊资料可以公开到群。

2. 岸岸直接在“全村人运营团队”发起待关联事项，UI 展示同一事项。展示申请人、实际入住人、待绑定账号的姓名/昵称、必要的脱敏线索及不确定点；无需工作人员重新录入台账。有权的秦托邦小客服工作账号或主管可选“是同一人”“不是”“信息不足”，有多个候选时选择正确对象。确认账号和目标群均可配置；小客服按获授权工作账号归责，不追溯轮班自然人。

   工作账号须在本欢迎事项的范围内被明确授予身份关联确认权限，不因此成为通用身份管理员，也不取得 PMS 办理权限。

3. 关联应明确覆盖“渠道账号 ↔ 人员/申请 ↔
   PMS 逐个实际入住人”。如果只确认申请与住宿对应，只能保存这段关系；缺少聊天账号或账号归属依据时，不能声称二花已认出群里的那个人。无候选或无法确认时保持待关联，由运营人员在原事项补充线索，不要求无法联系的住客必须先加好友。
4. 确认后自动保存来源引用、具体关联对象、确认主体、时间和版本，支持更正或撤销；以后聊天、入群复用有效关联。默认保存 Agent
   OS 的关联记录，不修改 PMS 住宿事实或飞书姓名、手机号。若需向来源系统写入引用，另按其接口与归属实现，不把“回写关联”扩展为改写原始事实。
5. 人员关联确认、卡片内容确认与发布分别记录效果，模糊一句“同意”不能替代不同效果的明确确认，也不能把一次“卡片可以”自动当成身份绑定。UI/群可以在同一事项集中办理，但必须让确认者看清这次具体确认什么。本栋欢迎词仍以舍长为优先；确认身份本身不授权欢迎内容发布。

居民自助核验仅作为已有可达私聊、且必要条件具备时的可选补充，不是默认路径或必经步骤。本轮不引入短信服务或额外身份证采集。尚需实现候选生成、运营群确认、关联落库和更正撤销闭环，并用真实群聊/私聊验证同一人一致识别；文档修订不代表业务已可用。

### 工作账号主体的现有实现差异（只读代码评估）

核对基线 b42db0d 的结果：现有 actor、授权和欢迎审计尚不能将工作账号作为独立主体完成确认。不能只移除一个 shared 拒绝条件就宣称支持，更不能给工作账号伪造自然人 Person。

| `person_collaboration/store.rs` 的 Actor / verify           | person 为必填 UUID；验证 JOIN 人员，并排除 shared gateway                                                                |
| `person_collaboration/store/identity.rs` 的 gateway_actor   | 必须解析 active Person；shared 账号直接报 shared_account_person_unknown                                                  |

| `resident_welcome/foundation.rs` 的 foundation_approve_as   | 入参为 person UUID，写 approved_by，审计固定 actor_type=human                                                            |

最小增量提案供总指挥协调，尚未实施：

1. 共同身份层显式区分 `person` 与 `work_account`
   主体。工作账号保持可信渠道/企业命名空间、有效状态及版本，不占用 Person。旧个人解析接口保持个人语义，增加面向已授权业务的主体解析，避免影响居民记忆/在住代理等依赖真实人员的行为。
2. 授权检查接受可信主体引用，工作账号只通过明确授予的欢迎运营确认、欢迎事项内身份关联确认动作与范围；不把旧个人授权自动复制给工作账号。主体必须由 host 会话解析，模型不能自报类型或账号。
3. 欢迎运营确认记录及命令幂等记录明确保存主体类型与引用，审计显示“工作账号确认”，自然人未知就不填自然人。使用新增迁移及数据设计，不改已应用迁移；具体表结构和迁移编号需与活跃任务协调。不能为了省字段把工作账号 UUID 塞进人员外键。
4. 本体线负责 `person_collaboration/model.rs`、`store.rs`、`store/identity.rs`
   及欢迎接收/审计的最小增量和必要迁移；宿主/工具只传可信上下文。岸岸继续提供来源、住宿、事项引用；其 PMS 确认保持既有检查，不自行删去个人验证条件来绕过共同接口缺口。公共 server/mod 改动先报总指挥。

上述增量仅定义需求和兼容方向，不代表已批准把所有业务改为工作账号确认。需覆盖本人账号兼容、工作账号伪造拒绝、精确权限、撤权、审计显示及本栋实际组合版本验证。
