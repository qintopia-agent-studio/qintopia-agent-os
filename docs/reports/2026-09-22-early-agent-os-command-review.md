## 确认目标与早期建议的区别

8 月 31 日，负责人明确提出：系统是团队与智能体共同运行的总线；应识别人、调度人的工作，区分谁能调用智能体、谁能指导工作习惯；开发应易测试、减少额外开销，只在必要时推送 GitHub。

9 月 8 日，负责人提出先推进统一人员基础。随后建议先做好可用、可纠错的身份及关联，再推进授权和协作，不等待所有历史档案填满。这个方向与当前 A/B→C→D 一致。

旧助手提出的具体四张新表、五种权限维度、完整飞书任务接入、独立策略系统选择、新检查命令以及
`human-agent-bus.md`

## 必须补入的有价值目标

### 1. 从人指导智能体，继续走到智能体与人交接工作

前一轮总指挥交接强调 C 的管理员设权、舍长指导二花和管理智能体分派；它们没有覆盖“将事项交给具体工作人员，接收处理结果，再继续业务”的全部目标。

本地基线 `0806c2e` 的实际证据：

- [operations 控制面](../../runtime/sidecar/src/operations.rs)已有 WorkItem、`human_owner`、工作台引用、事件记录及状态/审核/换负责人处理，不能称为完全没有回写基础。
- `report_from_request` 仍将 Feishu Task 计划标为
  `dry_run_only=true`，明确本命令不创建外部任务；记录负责人字符串不等于真实任务已可靠派给对应 Person。
- [协作模块](../../runtime/sidecar/src/person_collaboration/README.md)已能表达 Person、任职、职责、Agent 和范围，后续应复用；真实人类处理入口与统一任务消费未由本次源码核对证明贯通。

因此保留“人的任务闭环”为独立后续目标，已写入[实施计划 §6](../plans/active/person-agent-foundation-execution-plan.md#6-后续保留目标人的任务闭环)。它不自动扩大 C/D，也不强制先建完整飞书任务产品。

“不增加人的负担”继续适用：自动化负责整理、提醒策略和状态维护；人的参与限于原本必要的业务处理。不得借此给员工派发补全画像、登记来访或整理智能体记忆的工作。人的任务存在也不意味着每次状态变化都发送通知。

### 2. 将低开销开发偏好落实为协作节奏

已补入[协作约定](../engineering/collaboration-model.md#local-iteration-and-push-cadence)。

本地连续开发，优先目标包检查及已有 fixture；到可审阅阶段运行适用的项目检查，协作、远端 CI 或 PR 需要时再推送。

早期提议的 `pnpm check:changed`、`pnpm check:package` 并非当前 `package.json`
中的可用命令，不写成现成能力，也不为归档另造框架。已有 `check:pr:auto`
和业务测试入口可以复用；不承诺所有检查都在固定分钟数内完成，不省略风险要求的测试。

## 早期表述的适用边界与应避免的误读

| 旧表述/建议                                           | 处理                                                                                                                                                         |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ChannelIdentity(platform, channel_user_id, chat_id)` | 作为示意理解；账号身份依赖平台/企业/应用等命名空间，群是场景和成员关系，换群不应创建另一个 Person                                                            |
| 人员授权绑定稳定 `person_id`                          | 合理；人员操作和委托保留稳定 Person。Agent、服务执行主体仍有自己的身份与权限，不把系统主体伪装成自然人                                                       |
| 区分交谈、调用、审批、训练、信息访问五种授权          | 作为判断维度合理，不意味着照此固定新建五种管理类别或数据库表。复用当前职责/动作/范围模型；普通公开咨询和本人提供信息不要求先有员工岗位，不新增逐流程授权类别 |
| 四张新表作为统一授权方案                              | 不照搬。已有 `collaboration_appointments`、`agent_collaborations`、`collaboration_grants` 等；以需求缺口决定增量，避免第二套授权权威                         |
| Profile 承载“Agent 的局部工作习惯”                    | 需保留“局部”限定。Profile 可存 persona、技能和运行局部配置；共享人员事实、偏好、约定和授权交共同服务维护，按权限使用                                         |
| 所有外部发送/跨进程操作都建 WorkItem                  | 持久交接、等待、审批和恢复应有任务；即时问答和查询不为了形式逐条建异步任务，外发本身仍需相应授权与审计                                                       |
| 建议用真实飞书任务补齐人的工作闭环                    | 是候选实现，不是负责人确认的唯一入口。业务目标是可靠交接与结果回写，现有内部工作台和渠道均需评估复用；不先扩大集成范围                                       |
| Postgres 是系统事实源                                 | 需按领域限定。业务控制事实、调度声明、住宿事实分别遵循 Agent OS、Hermes cron 和 PMS 的权威边界，关键执行结果汇入 Agent OS                                    |
| 高风险外发需人审                                      | 保留适用风险边界，与有效持续授权内的普通欢迎不冲突；不能扩大理解为每次欢迎都加人工审，也不因此放开其他公开发布或隐私许可                                     |
