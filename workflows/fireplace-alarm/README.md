# 一楼壁炉区烟雾与一氧化碳报警

收到壁炉区已登记报警器的涂鸦属性事件时，四老师负责全村人运营群，二花负责社区群。紧急撤离文案从[共享环境 Skill](../../skills/qintopia-tuya-sensors/references/alarm-messages.json)
读取。工作群另有当班同事清点人员、确认报警、提供被困位置的分工。

| 设备上报或投递结果                     | 处理                                                                                           |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 新的烟雾或一氧化碳报警                 | 立即通知两个群，各自从首条计时，在约 30 秒、60 秒时再提醒，每群最多三条完整撤离通知。          |
| 同次上报两项报警，或本轮新增另一种危险 | 发送合并通知。已发过首条时立即占用下一次提醒名额。重复上报沿用本轮计数。                       |
| 一项恢复，另一项仍报警                 | 后续提醒只写仍在报警的危险。                                                                   |
| 本轮报警的各项均上报正常               | 取消剩余撤离提醒，向有撤离通知成功回执的群各发一次设备状态更新。返回建筑须等现场救援人员确认。 |
| 正常自检、电量、故障、联动字段         | 只记录。自检同时明确上报烟雾或一氧化碳报警时照常处理。                                         |
| 旧事件、重复投递、服务重启             | 用启用时间、每项设备时间、持久化提醒名额去重。延迟投递可用更新的云端正常上报取消过期提醒。     |

## 路由和投递

设备 ID 从主机注册表中唯一匹配「一楼壁炉区」的 `smoke-co-alarm`
类型设备。群地址只取自主机受控路由配置。四老师对应 `wecom`，二花对应
`qiwe`。两个发送进程独立处理各自的投递记录。发送前先将名额写入 SQLite，调用 Hermes 后记录平台回执。超时或进程在发送中退出时保留未确认状态，避免重启重发同一条。未确认项目可按事件、profile 和提醒序号核查。

每个群按自己的上一条提醒决定是否提前发送。另一种危险在取单前已经恢复时，保留原来的 30 秒和 60 秒提醒。短暂的新报警若在两次取单之间已经恢复，仍保留此前已收到撤离通知的群所需的最终恢复通知。较新一轮的撤离通知获得该群回执后，由较新一轮负责收尾。

只有在本机明确未能启动 Hermes 时才重试同一条通知。连续启动失败时，前三次重试分别间隔 5、25、30 秒，此后每分钟最多重试一次。每次重试前都核对当下的报警状态及该群仍需发送的通知。该规则同样适用于恢复通知。超时、缺失回执和进程中断均保留原名额。

延迟补查同时读取两项危险的状态和设备上报毫秒数。发现尚无对应推送的云端报警时，暂停恢复通知，直到订阅收到对应报警或更新的正常上报。新的撤离通知始终由设备订阅事件触发。

## 当前阶段与验收

审阅版本不安装服务、不注册定时任务。原订阅仍负责接收。下列模拟验证使用临时数据库和替代发送器。

```sh
python3 -B -m unittest discover -s workflows/fireplace-alarm/tests -v
```

后续启用时由同一订阅消费者在消息确认前提交报警状态。订阅接收身份和两位智能体的发送身份分别使用各自的现有权限。上线前需核对设备注册、两个固定群、当前唯一消费者、持久化数据库、开关及回退版本。停用发送端后可恢复原接收器，保留投递记录。实机和群内演练另按授权验收。
