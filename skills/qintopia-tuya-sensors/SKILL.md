# 秦托邦环境监测与报警

用户问现在的温湿度或想比较楼层时，调用 MCP 服务 `qintopia-sensors` 的
`read_environment`。按地点填
`area`，例如「一楼壁炉区」或「3楼活动区」。比较两个楼层时省略
`area`，一次取得所有已登记设备的最近读数。遇到不熟悉的地点，用同一服务的
`list_sensor_areas` 核对名称。

用户问烟雾报警器、烟雾或一氧化碳报警状态时，同样调用 `read_environment`，把 `area`
填为「烟雾报警器」。分别报告两项状态（`alarm` 为报警，`normal`
为正常）及各自上报时间。云端上报无法确认现场是否仍在报警。

按区域回答每一项的 `value`、`unit` 和
`reported_at`。数值已换算，时间为北京时间。`queried_at`
是请求云端的时间。较早的读数请带上实际日期和上报时间。

设备可能部分成功，可分别报告。`not_reported` 表示尚无上报值，`unit_unconfirmed`
表示温标待核实，`time_unknown` 表示有读数但缺少上报时间。有本机终端工具的会话也可以执行
`/usr/local/bin/qintopia-sensors read --all` 或按设备名查询。

## 壁炉区报警通知

服务器订阅这台报警器的涂鸦属性推送。以下是报警工作流启用后的群通知规则。普通查询只向提问者回复，避免人工补发造成重复。回答「自动通知是否已启用」时，核对工作流的实际发布和启用记录。

- 新上报的 `smoke_sensor_state=alarm` 或 `co_state=alarm`
  启动撤离提醒。四老师发全村人运营群，二花发社区群。工作群另附当班同事的清点和报警分工。
- 每群每轮最多三条。首条立即发送，后两条在首报后约 30 秒、60 秒提醒。收到另一项报警时，立即在剩余名额内发合并提醒。重复上报沿用本轮计数。每条带完整撤离指令、设备上报时间和提醒次数。
- 只恢复一项时，后续提醒写仍在报警的项目。本轮报警各项都上报正常后，停止剩余提醒，向已通知的群各发一条设备状态更新。是否返回由现场救援人员确认。
- 自检成功且两项正常、单独的电量、故障、自检或联动字段只记录。自检期间另有明确的烟雾或一氧化碳报警，仍按对应危险处理。设备的历史查询结果不触发群发。

需要查看群内原文时，读取
[报警通知文案](references/alarm-messages.json)。用户询问某条群消息是否发出时，以对应群的发送回执为准。
